# MPCFEAS — can a dawn rollout planner be COMPUTED inside the live agent?

2026-09-18, worktree `mpcfeas` off `4be2450`, tools `S/mpcfeas/`. Local only, CPU.
PLANSELECT (`docs/strategy/2026-09-17-planselect.md`) left the oracle standing: best-of-8
banked plans is **+3,193/board t 5.7**, and which plan wins is a BOARD property (seat-0
argmax keeps 93-100 % on seat 1). Prediction from rival tells realised ≈ 0. This box asks
whether *computing* the argmax — K forward rollouts at dawn — fits the live agent.

## 1 Time budget (measured, `S/mpcfeas/time_agent.py`)
`kaggriculture.json`: `episodeSteps 720`, `actTimeout 1`, `remainingOverageTime 60` — and
the bank is **in the observation**, so the agent can read it. `core.py:631` deducts only
`max(0, duration - 1)` from it; `agent.py:220` marks TIMEOUT (reward `None` = loss) the
moment a call's excess exceeds the remainder; `agent.py:89` hard-kills at `bank + 1 + 1`.
The bank is therefore **one 60 s pool of overtime for the whole game**, not per turn.

Shipped agent, one real 720-step episode, both seats (`submission/main.py` + `theta.npy`):

| | n | mean | max | total |
|---|--:|--:|--:|--:|
| hour 0 (`build_day`) | 60 | 95.2 ms | 119.9 ms | 5.71 s |
| hours 1-23 (replay) | 1378 | 0.1 ms | 45.9 ms | 0.08 s |

Episode wall 12.0 s, agent 5.79 s of it. **d0h0 = 116.5 ms, leaving 60.9 s of slack.**
There is no jit in the package at all: `agent/runtime.py` calls `P.build_day(np, view,
macro)` — the ~204 s compile belongs to the JAX ES/sim path the package never imports.
Later days get `1 s − 0.10 s = 0.9 s` each once the bank is spent. **MPC is a day-0-only
device; "a few later days" is not purchasable.**

## 2 RNG — the seed is scrubbed AND the board is deterministic
`kaggriculture.json` says it outright: the interpreter *"clears this from configuration
after reading and stores the resolved seed on `env.info['seed']` so it stays out of agent
observations but is still recorded in the replay"*. `resolve_episode_seed` defaults to a
random **31-bit** int → 2^31 space.

Grepping all 1,086 lines: the **only** seeded randomness is `kaggriculture.py:871`
`random.Random((seed * 1_000_003) ^ day)`, consumed at `:839` (weed, p 0.005 per empty
unlocked tile) and `:891` (`rng.choice(sorted(SHOPS))`, 3-daily). `_initialize`,
`_new_farm`, `_initial_tile`, `_default_spawn`, `_new_market`, `_new_town` take **no rng**:
**every episode starts from a byte-identical board.**

Two consequences. (a) At day-0 dawn the observation carries **ZERO seed bits** — brute
force is not expensive, it is *undefined*, there is no constraint to filter 2^31 seeds. The
first bit arrives at day-1 dawn (≈ 0.25 expected weeds/seat/day); 3 bits at day-3 (first
shop). (b) The shop word's offset is `2 * used` where `used` is the empty-tile count
(`sim/eod.py:267`), so **the plan under evaluation moves its own shop draw** — the board
key is endogenous, not merely hidden. This also **refutes PLANSELECT §4's surviving
hypothesis**: there is no "our OWN day-0 draw (tiles, quadrant, shop timing)" to condition
on. The oracle is keyed to the weed+shop stream, all of which starts *after* day 0 closes.

Ranking stability across re-rolls (`S/mpcfeas/rank_stability.py`, real engine, K = 4 plans
× 6 seeds, mirror opponent, 24 games / 311 s):

| | value |
|---|--:|
| pairwise argmax agreement across re-rolls | **0.20** (chance 0.25) |
| within-plan sd across seeds (the lottery) | 1,857 |
| spread of the four plan means | 3,085 |
| oracle(perfect argmax) − best-fixed, 6 seeds | 716 (sd/√6 = 758) |

Argmax is **at or below chance**. A day-0 rollout that guesses a stream ranks no better
than a coin.

## 3 Sim speed on CPU
No pure-numpy 30-day rollout exists: `sim/rollout.py` is JAX-only (79 `jnp` sites plus
`lax.scan`/`lax.cond`); only `sim/eod.py` is `xp`-generic. `scripts/bench_sim.py 1` under
`JAX_PLATFORMS=cpu` did **not finish a single compile in > 20 min** (killed) — the jit path
is out at any budget. The usable rollout is the **real engine itself**, importable in the
package: **13.0 s per full 30-day game** (311 s / 24), of which ~6-7 s is the interpreter
and ~2.9 s/seat is our own `build_day`. Against a tape opponent ≈ 10 s. So **45 s of the
60 s bank buys K = 3-4 here, K ≈ 2 on Kaggle's 1.6 vCPU**; K = 8 costs ~80-104 s, 1.3-1.7×
the entire bank.

## 4 Opponent model — the one green light
`scripts/tape_opponent.py` already packages any recorded seat as an agent runnable on a
**NEW** board, and its docstring states the reason re-derived above: every farm starts
identical, the seed randomises town/weeds/prices but *not a single tile coordinate the tape
names*. The band is one open-loop clone (`kaggle-clone-family`), so one tape covers 60-75 %
of live opponents; V44-V48 sources are decoded in `S/nbintel/`. Engine class: tapes only,
but tapes are sufficient for the same reason. Cost is O(1)/turn. The error is one-sided —
a tape cannot react, so only OUR purse moves, which is exactly the TWO-PURSE violation that
has made every counterfactual in this project overstate.

## 5 Gain under realistic error — **NO-GO**
Realisable = oracle × (P(argmax right) − 1/K) = 3,193 × (0.20 − 0.25) ≤ 0. The selection
carries no information because the quantity it would condition on does not exist at day 0.
Against that: one 45 s day-0 call on an unknown-speed worker, against a 61 s threshold that
scores the game a **LOSS**. At a 2× derate the K = 3 call is 90 s — a certain loss; even a
2 % timeout rate costs ≈ 2 wins per 100-game rating window. Cost is real, gain is zero.

**NO-GO. The in-game rollout planner family is CLOSED, and with it PLANSELECT §4.** No
first task. The only durable residue is a fact worth reusing: we spend 0.12 s of a 61 s
day-0 allowance and the bank is readable from the observation — any future day-0 compute
has ~45 s to spend, but it must condition on something that exists at day 0, and the
engine says the only thing that exists is the opponent.
