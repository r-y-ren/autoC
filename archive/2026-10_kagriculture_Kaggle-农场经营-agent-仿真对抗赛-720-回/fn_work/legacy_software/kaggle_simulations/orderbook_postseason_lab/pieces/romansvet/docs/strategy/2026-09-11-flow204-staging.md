`LR=<x>` overrides, and any σ outside the E3 grid is refused rather than guessed at.

## Why the two numbers have no defaults

They are a **measurement** — the PASS row of `S/onestep/sweep_b.txt` — not a preference. A default
would let the arm start on the σ/P the campaign has already run twelve times, which is precisely the
failure §48 was written to stop. The launcher therefore `exit 2`s unless both are supplied, names the
file to read them from, and points at flow203 if the sweep failed instead. It also refuses a σ off the
grid, a non-integer or odd `POP` (the estimator is antithetic: `half = pop // 2`), and a `POP` off the
grid unless `POP_ANY=1` is set deliberately.

## Memory: pop 2048 fits a 24 GB card at the unchanged `--chunk 8192`

Established from the arm build's code, not guessed. `Trainer.batch_eval` builds `pop × episodes`
rollouts and evaluates them in shards of `step = (chunk // n_devices) * n_devices`, so peak memory is
**chunk-bound**: the per-call working set at `--chunk 8192` is identical at pop 2048 and pop 512, and
only the shard count per generation changes (91,648 → 366,592 rollouts = 12 → 45 calls). Pop grows
three resident arrays: `thetas` [pop, 6789] f32 13.9 → 55.6 MB, `eps` [pop/2, 6789] 7.0 → 27.8 MB, and
the per-generation result block [pop, 179, 12] int32 4.4 → 17.6 MB — **≈ +80 MB**.

Measured reference: `S/localarm/gpumem_8192.log`, the same argv at pop 512 / chunk 8192 / episodes 160,
peaked at **6,049 MiB** on the 8 GB local 3070 over a 1,184 MiB idle baseline = ~4.9 GB of process
memory. pop 2048 therefore sits at **~5.0 GB of 24 GB**: **no chunk flag, no reduced `--episodes`**.
`CHUNK=<n>` stays available as an escape hatch only — the trailing shard is padded and the padding is
discarded, so chunking costs wall time, never results.

The real cost of P 2048 is **wall**: 4× the rollouts per generation ⇒ ~3.7 min/gen on the 3090 against
~55 s/gen at pop 512, ~19 h for a 300-gen short arm. That is why §6 says to prefer a passing P 512 cell.
