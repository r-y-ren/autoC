## 1. Harness design (`S/bcsim1/fastenv/`)
- **Engine** `sim.hpp` + `pyrandom.hpp`: the public nikital7 C++17 port ("4000x environment speedup | Kaggriculture", Apache-2.0), extracted verbatim from the notebook dump, plus ONE patch for kaggle-environments 1.32.7: the `hinge` price shape (`u + 8*max(0, u-1)^2`, `u = x/T`) now used below I0 by CARROT (target 1.00), TOMATO (0.40) and EGG (0.40). Without it the first mismatch is the step-1 CARROT price (36 vs 35). All patch lines carry a `BCSIM1` comment.
- **C ABI** `kagapi.cpp` -> `libkag.so` (`g++ -O2 -std=c++17 -shared -fPIC`): `kag_new(seed)`, `kag_set_town`, `kag_step(a0, a1)` on int-coded actions, `kag_export` (flat int32 state).
  - Town pin identical to `scripts/town_inject.py`: after the engine's own end-of-day (weeds and the shop draw consume the RNG exactly as usual) the shop list is overwritten with `[shop for (d, shop) in town if d <= next_day]`.
- **`kag.py`** (ctypes):
  - Action encoder mirrors `kaggriculture._apply_unit_action` / `_parse_order` parsing (malformed -> no-op codes; PICKUP/PLACE default qty 1; market qty > 2^31 clamped, since one tape sells 2^53-1).
  - Observation builder returns kaggle-shaped dicts (tiles with the exact key sets: an empty structure has no `animal` key; plant / animal fields; per-unit inventories in insertion order).
- **`harness.py`**: N games in lockstep, clone in our seat vs the board's open-loop tape (`S/pool1/bank/<tape>/main.py`, one fresh module per env so its hire-alignment state is per game).
  - Per step: python features per env (`feats.grid_glob`).
  - Then model3 sequential decoding, one batched JAX call per unit slot k for ALL envs. The ego crop and the prior claim/destination maps are built on device from the 10x10 grid, the unit position and the earlier units' (x, y, tok+1) list, exactly as in `train3.py`.
  - Per env: legal mask (all-44 version of `main._legal`) and masked argmax (or a masked-softmax sample at temperature T).
  - One batched market forward per step.
  - Then the agent's OWN overlay functions from `S/bcbody1/agent/main.py` (`_guard_units`, `_care_units`, `_cap_market` with that env's ledger swapped in, `_care_market`, `_endgame`), config r4c = `BCB_GUARD=1 BCB_WATER1=1 BCB_CARE=2 BCB_CAP=90 BCB_END=1 BCB_M3=1`.
  - Modes: `ref` calls `main.act()` per env (engine + plumbing proof). `np` is the batched decode with the agent's own numpy forward per unit (same op shapes). `jax` is the batched forward, GPU or CPU, `Precision.HIGHEST`.
  - `sample=True, record=True` stores everything PPO needs: per env-step grid u8 + glob f16 + 21 market classes + their log-probs; per unit decision [step, day, k, x, y, tok, qty, inv12] + prev tok + prior list + legal mask + log-probs.

## 2. Bit-exactness proof
- **Engine:** `replay_check.py` replays each recorded replay's joint actions (town pinned from the replay's own unlock list) and compares the full observation of both seats (farms incl. every tile dict, private shed/seeds/inventories, market inventory+prices, town, day, hour) at every step.
  - 12 r4c MELON replays: ALL_EXACT (`replay_check12.log`).
  - 10 r4c teacher + 8 r4c MELON replays: ALL_EXACT (`replay_check_more.log`).
  - 7 V56-body diag / teacher-market replays: ALL_EXACT (`replay_check_v56.log`).
- **Closed loop:** `play_ref.py` (copy of `S/bcbody1/play.py`) re-ran 3 MELON seats with `params_r4c.npz` and r4c switches (`ref3.csv`: 91,889/27,785, 96,536/128,173, 81,724/109,357 = the r4c csv). `compare.py` checks our seat's 719 actions against the replay and the final money of both seats:

  | harness mode | first action divergence | final money |
  |---|---|---|
  | ref (main.act in the C++ engine) | none (719/719 x3) | identical |
  | np (batched decode, agent numpy forward) | none | identical |
  | jax CPU batched | none | identical |
  | jax GPU (3090) batched | none | identical |

- **Full rung:** the PPO u0 greedy eval (6 GPU workers, batched) reproduces the python-engine r4c rung on all 30 boards (20 MELON + 10 teacher). Both seats' final money match, and the teacher ratio is 0.825. Because the fast env is exact, `greedy2ladder.py` turns any `greedy_<u>.json` into a BCBODY3 ladder row with no python-engine run.
- One bug was found and fixed during the proof: the JAX rollout first passed raw tokens to the prior maps where `train3.py` uses tok+1. Before the fix, all 3 boards diverged at step 3. It is in the jax proof log history.

- Next speedups:
  - vectorise `grid_glob` from the exported int32 state instead of dicts (about 2x);
  - more worker processes (8 remote cores cap it now).

## 4. PPO fine-tune (`S/bcsim1/fastenv/ppo.py`, remote GPU1)
- **Rollouts:** 6 spawned workers, each runs `harness.run(sample=True, record=True)` on its env slice with a batched JAX forward. Sampling temperature is T=0.5; the bench below is why.

  | policy (60 train seats) | mean margin | W |
  |---|---|---|
  | greedy (argmax) | -17.5k | 16/60 |
  | sampled T=1.0 | -26.4k | 13/60 |
  | sampled T=0.5 | -21.2k | 15/60 |
  | sampled T=0.3 | -22.3k | 14/60 |

- **Envs:** the 20 MELON seats of `boards_eval.json` plus the 40 newest other MELON band seats of `S/bandbank2/boards_band2.json` (`boards_train60.json`). The 56 remaining MELON band seats (`boards_hold.json`) are held out. N=128 per update.
- **Objective:**
  - PPO clip 0.2 on every sampled decision: the unit token over the legal mask, PICKUP/PLACE qty, and the 21 market heads.
  - Reward R = (ours - theirs) * 1e-4 + 1.0 * win.
  - Advantage = R minus the mean R of the same board in the batch (group baseline), normalised.
  - KL(pi || pi_BC) coefficient 0.05, entropy 0.001, 4 epochs, minibatch 4,096 unit rows, Adam 1e-5, clip-norm 1, learner precision HIGHEST.
  - Batch: ~850k unit decisions + 92k market steps per update.
  - The first-minibatch clipfrac is 0.005, so the rollout and learner log-probs agree.
- **Greedy eval** every 5 updates on all 126 boards (60 train + 56 held + 10 teacher). It is exact, so it IS the ladder: `greedy2ladder.py` gives the BCBODY3 row. Params are saved every 10 updates.
- **Wall:** roll 52 s (2.46 games/s) + learn 49 s (all heads) or 5 s (market only) per update. The first update is slower (compile).

## 7. Incidents
- **Remote reboots.** The remote hard-rebooted at 14:06Z and 14:46Z (`last -x`: no clean shutdown). Both times both 3090s were loaded:
  - 14:06: BCBODY4 on GPU0 + GPU1.
  - 14:46: BCBODY4 on GPU0 at 100% + this stream's learner starting on GPU1.
  - Suspect: the PSU trips under dual-GPU load. After the reboot GPU0 stayed idle and the PPO ran on GPU1 alone with no further incident. **Do not run heavy jobs on both GPUs at once until this is checked.**
- **Moving the learner local does not work.** The local RTX 3070 would need ~500 MB of rollout data per update, and LAN scp runs at ~2 MB/s.
- One tape (held-out set) submits SELL qty 2^53-1. kag.py clamps market qty to int32; this is harmless because shed and purse bound it.

## 8. What BCBODY5 should run next
1. **Use the fast env as THE ladder judge.** It is exact.
   - A 126-board rung (60 train + 56 held MELON + 10 teacher) takes ~1-3 min on remote GPU1 with 6 workers (2.5 games/s after warm-up). The python engine needs ~12 min for 30 boards.
   - Sweep the overlay knobs (care thresholds, cap percentile, END hour, the invest/sale switches BCBODY4 is adding) and new BC params on 116 MELON seats instead of 20. That makes W/flip counts twice as precise.
   - `harness._decide` wires only the r4c overlays (GUARD, WATER1, CARE, CAP, care market, END), calling the agent's own functions. SCHED / INV / SALE / D1HIRE / TAU are NOT wired yet: add each in the same order as `main.act()`. Then re-run `proof.sh` with that switch on to keep the exactness proof green.
2. **Do not re-run terminal-reward PPO.** For RL to have a chance it needs:
   - a critic and a dense per-day reward: the daily margin delta, with GAE instead of one episode advantage over ~850k decisions;
   - 10-50x more games. Vectorise `grid_glob` from the int32 export (python features are 45% of rollout time). Use 8 workers. Use GPU0 only once the reboot question is settled.
   - The cheapest RL-like lever first: **search over the few market knobs per board class in the exact sim** (e.g. cap percentile x HIRE schedule x END hour, a full grid on 116 seats). Then distil the winning knobs.
3. The MELON leg is a sale-pressure problem (dtheirs stays +12k..+17k vs V56 in every checkpoint). No clone-weight change moved it. The KERNEL2-style composition (clone d0-d9 body + V56 sale/end layer), measured in the fast env, is the next rung.
