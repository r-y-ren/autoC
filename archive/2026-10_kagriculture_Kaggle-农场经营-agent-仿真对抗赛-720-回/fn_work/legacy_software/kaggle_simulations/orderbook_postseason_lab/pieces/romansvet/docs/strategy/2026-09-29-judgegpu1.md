# JUDGEGPU1 (2026-09-29 09:49-11:29Z): the closed-loop judge's clone heads on GPU1, bit-identical

The enabling step from TRAINREVIEW1: move the reacting clone rival's forward pass out of the CPU judge workers.
Code and logs: `S/judgegpu1/`. Judge change: `S/reactclone1/judge.sh` (`--rival-device`) and a 6-line env-guarded hook in `S/reactclone1/rc.py`.

## Verdict
- **Bit-identical.** PFS vs the g0capsfix rival, boards_m40 0-3 x both seats (8 games): the GPU path equals the CPU path on
  - rows: 8/8 (every money column: ours, theirs, h1, d10, d18 cash);
  - the joint action sequence of BOTH seats, per step: 8/8 games, 5,752 steps (sha1 per step, `actlog.py`);
  - and both paths equal JUDGERIVAL1's baseline rows `S/judgerival1/res/g0capsfix/pfs.csv` 8/8, so the CPU path is unchanged.
  - The GPU logits are NOT bitwise equal to the CPU logits (max |diff| <= 1e-4); the decisions are argmax, and no argmax flipped.
- **Default = gpu1** in judge.sh. `--rival-device cpu` keeps the old path. If the server cannot start, judge.sh falls back to cpu (same rows).
- **More identity:** 24 games (boards 0-11 x 2 seats) at GPU batch shapes 12, 6 and 4: rows 24/24 and actions 24/24 (17,256 steps) each vs the CPU sweep,
  all 24/24 == the baseline. Clone body (two server connections, elite params): 8/8 rows == BCBODY8's GPU rows b8g_elite_gcf.
- **The gain is 1.2-1.7x, not 4-5x.** Games/s at 2 / 4 / 6 workers: 0.081 / 0.162 / 0.224 on gpu1 vs 0.070 / 0.119 / 0.130 on cpu.
  Per game: 10.4-11.3 worker CPU-s instead of 18.7-21.4.
  Our PFS planner stays on the CPU and is now the floor, ~8 CPU-s per game.

## 2. Design: one persistent inference server on GPU1 (option b)
- `S/judgegpu1/fwdserver.py`: one process on GPU1 builds the very same `kh.Forward(params, 'jax')` (same module, same jitted `mfwd` / `ufwd`)
  and answers the workers over a unix socket. One request = one call with the worker's own batch shape; no cross-worker batching, so a row
  never depends on what else runs.
- `S/judgegpu1/fwdclient.py`: `RemoteForward`, a drop-in for `kh.Forward` inside the worker. `kh._decide` is untouched: it still decodes,
  runs the qty head in numpy and applies every overlay on the CPU. The step's grid is sent once with `mfwd` and reused by that step's `ufwd` calls.
- Params: the server loads the path the worker names and checks the sha1 of the float32 arrays against the worker's; BCSIM_PREC must match.
- rc.py: `if os.environ.get('RC_FWD_SOCK')` -> RemoteForward, else the original line. Every wrapper that runs rc.py (rcr.py, dr_log.py,
  mp_rc.py, bs2_rc.py, cs_rc.py, ...) gets the GPU path by exporting RC_FWD_SOCK.
- Why not per-worker JAX on GPU (option a):
  - every worker would be a GPU launch: flock + 90 s each, so 6 workers take 9 minutes to start;
  - the worker's whole process would move to the GPU, including any JAX inside our own tree (kagg3.core.residual_head imports jax);
  - each worker would carry its own CUDA context (~250-400 MiB) and its own compile of every batch shape.
- The server was started once through the GPU law lock: `flock -o /home/user/gpu_launch.lock -c '<launch>; sleep 90'`.
  `-o` stops the server from inheriting the lock fd; without it the lock would be held for the server's whole life.

## 3. Costs of the GPU path
- Round trip per call: 2.3-2.8 ms, flat in the batch (B 8 / 14 / 40). mfwd 1.8-4.4 ms.
  - Per game-step that is ~11 calls / N games, so a large N matters: ~2.6 s per game at N 8, ~1.5 s at N 14, ~0.5 s at N 40.
- Server CPU: 1.6-1.8 ms per request (spaced or back-to-back), 0 % idle.
  - A NEW batch shape costs ~45 CPU-s and 10-35 s wall (XLA GPU compile), once per server lifetime.
- GPU1 memory: 404 MiB after the first shape, 538 MiB with 6 shapes and 2 params. Cap XLA_PYTHON_CLIENT_MEM_FRACTION .06 (1.47 GB), preallocation off.
- Worker CPU on the GPU path: 84 s user for 8 games = **10.5 CPU-s per game** (ours ~8, rival rest ~1.5, socket ~0.3), vs 19.2 on the CPU path.

- **Games/s gpu1 vs cpu:** 1.15x at 2 workers, 1.36x at 4, 1.72x at 6. The cpu workers load the shared box harder (load up to 18.8).
- The sweep.tsv column server_cpu_s is contaminated: CLSEARCH1's workers used the server from 10:32Z. Use the controlled 1.7 ms per request (`logs/srvcost_gap.txt`).
- **Add the server's CPU:** ~9.7 requests per lockstep step x 1.7 ms / N games. That is 3.0 CPU-s per game at N 4, 1.0 at N 12 and 0.85 at N 14.
- **Per core:** 18.7-21.4 CPU-s per game on cpu vs 11.4 (N 12) to 14.3 (N 4) on gpu1, i.e. 1.5-1.8x more games per core.
  At 2 workers the wall gain was only 1.15x: during the gpu1 run the load rose and our planner got less CPU (ours 227 s vs 165 s).
- **The fwd share of a worker's wall drops from ~49 % to 12-30 %.**
  - It is a fixed ~30 s per 719-step batch (per-step latency, not per-game), so a small N wastes it.
  - At N 4 it is 30 % of the wall; at N 12, 12 %.

## 5. Usage (for the other streams)
- Judge: `bash S/reactclone1/judge.sh [--rival g0capsfix|flood|big] [--rival-device gpu1|cpu] <tree_src|params.npz> <tag>`, then
  `bash S/reactclone1/judge.sh collect <tag>`. gpu1 is the default; it starts the server if it is down (one GPU launch through the lock).
- Own wrappers: `bash S/judgegpu1/jgserver.sh start` once, then export
  `RC_FWD_SOCK=/home/user/stage_reactclone1/S/judgegpu1/run/fwd.sock` in the worker's env (keep JAX_PLATFORMS=cpu).
- Server: `bash S/judgegpu1/jgserver.sh status | stop`. stop refuses while workers are connected. The server exits after 12 h idle.
- **Limits for the other streams.**
  - Keep N >= 12 games per worker batch on gpu1: the forward costs ~30 s per batch whatever N is.
    - For 80 games: 4 workers x N 20, or 6 x N 14.
  - At most ~8 workers in total on the one server, across all streams:
    - it is one Python process, 1.7 ms CPU per request, a ceiling of ~500 requests/s;
    - 6-8 connected workers (CLSEARCH1 + this sweep) drew 277 requests/s at 10:41Z.
  - Each new batch shape costs ~45 CPU-s and 10-35 s of wall once per server lifetime (XLA compile).
  - After a server restart (autotuning is redone), re-run the 8-game identity check:
    - `bash ../judgegpu1/jrun.sh <tag> gpu1 1 8 4` on the remote, cwd S/reactclone1;
    - then locally `python S/judgegpu1/cmp.py S/judgegpu1/res jg_id_cpu <tag>` after pulling res.
  - The GPU logits differ from the CPU logits by <= 1e-4. So far there are 0 argmax flips (88 GPU game-runs = 32 distinct games, batch shapes 4/6/8/12, 2 bodies), but it is argmax
    stability, not bitwise equality.
