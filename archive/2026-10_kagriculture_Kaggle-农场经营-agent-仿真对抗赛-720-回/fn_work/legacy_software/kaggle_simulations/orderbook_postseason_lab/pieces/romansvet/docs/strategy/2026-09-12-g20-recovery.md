# flow211 / flow212 g20 centre recovery (2026-09-12)

## Recovery state

Both archived checkpoints are intact (`state_g00020.npz`, about 5.68 MB each).
The earlier g20 attempt produced logs containing only screen setup banners (and
one stop request), with no CSV or JSON result.  Those logs are partial and are
not evidence.  The complete g10 artifacts were left untouched.

A bounded two-process CPU run of the arm-rung reader was started directly,
without `centre_read.sh`, so it cannot append the shared verdict log.  It uses
two processes, `OMP_NUM_THREADS=2`, `JAX_PLATFORMS=cpu`, chunk 32, the archived
g20 theta in memory, and writes only into each flow's owned directory.  At the
original tool sessions were:

- flow211: exec session `70250`
- flow212: exec session `77701`

Both processes terminated with exit code 1 and produced no result files. Host
PIDs 82306 and 82309 are gone. The failure occurred after Trainer setup, before
any episode evaluation: changing `obj_rungs.py`'s global `O` redirected both
outputs and its required input, so `families()` raised `FileNotFoundError` for
`S/snr/<flow>/rungmap.csv`.

`S/snr/recover_g20.py` is the durable repair. Before importing the shared
driver or initializing Trainer it validates the allowed arm, exact g20 archive
and generation, `(6789,)` float32 theta, canonical rung map, launcher, source
tree, B theta, and absence of a completed output. It keeps
`S/objaudit/rungmap.csv` as the input while routing results to the arm's owned
directory; no copied input or shared-driver edit is required. Both arm
preflights pass.

Run the reads with unbuffered output and durable logs (two workers maximum):

```bash
JAX_PLATFORMS=cpu OMP_NUM_THREADS=2 timeout 1800 \
  .venv/bin/python -u S/snr/recover_g20.py flow211 \
  > S/snr/flow211/recover_g20.log 2>&1
JAX_PLATFORMS=cpu OMP_NUM_THREADS=2 timeout 1800 \
  .venv/bin/python -u S/snr/recover_g20.py flow212 \
  > S/snr/flow212/recover_g20.log 2>&1
```

Run these concurrently only if the total CPU allowance permits two processes;
each command itself is configured for two CPU threads. The runner uses chunk
32, `/root/tree_famgrad`, the expanded flow211 launcher, and the per-arm tag
`centre_<flow>_g20`. This staging repair does not change evaluation semantics.

Expected completed files are
`S/snr/<flow>/obj_rungs_centre_<flow>_g20.{csv,json}` and the corresponding
`obj_money_*.npz`.  Absence of the JSON means the family read is incomplete.
