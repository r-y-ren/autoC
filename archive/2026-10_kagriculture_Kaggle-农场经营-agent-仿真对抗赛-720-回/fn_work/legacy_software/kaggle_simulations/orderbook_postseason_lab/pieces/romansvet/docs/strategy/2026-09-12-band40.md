# BAND40 — 40 fresh pinned-town tapes in the LIVE-C band (2350-2650), and the first paired leg

2026-09-12T02:4xZ. Built by the tape agent; toolkit `S/band40/`, README `S/band40/README.md`.

## 0. Why
`docs/strategy/2026-09-10-consensus.md §107/§110` and `docs/strategy/2026-09-12-objective-gate.md`:
the ES step away from candidate B **sells** margin on the band families (LIVEC42 = LIVE-C ids 1-42,
pinned-town, opponents 2300-2615, mean 2457; W2 = 85 old-band tapes ~1900-2100) and **buys**
top-ten / LOSS10 margin. Reading that trade per family at |t| ≥ 2 needs ≈ 59 LIVEC42-class boards;
we had 42. BAND40 is the missing support, and — being pinned-town rungs one per fresh team — it is
also the band-only rung family the next objective arm (flow212) wants to train on.

  the team filter; our own four submissions are excluded as teams AND as opponents.
* Stratified over the **2350-2600** sub-band (474 fresh teams) every 9th by rating → 48 candidates,
  so the overlap with NEXT30 (2550-2750) is only the thin 2550-2600 sliver. Realised span
  **2598.7 … 2374.2, mean 2482.8, median 2480.8** — i.e. the LIVEC42 band, essentially on its mean.
* One episode per team: the most recent COMPLETED non-VALIDATION episode that team **won**
  (narrow-loss ≤ 5 % was the fallback and **was never needed: 48/48 are wins**), never against one
  of our submissions, never an id we already hold. All 48 episodes ended **2026-09-12T00:23Z-02:21Z**
  — the file that is on the ladder right now. We replay **their** seat; our theta plays the other.
* 40 selected as BAND40 (`ids.txt`), evenly spread by rating; the other 8 queued in `ids_ext.txt`.

**One honesty note on the team filter.** The exclusion set folds in *opponent* names as well as
tape-seat team names (261 names in all), and the filter compares the **leaderboard**'s `teamName`
while the recorded `team` column comes from `ListEpisodes`; for three teams those two spellings
differ, so three BAND40 rows carry a name that is in the exclusion set:
`Sai Reddy Pothireddy` (2576.1, ep 108019440), `dont share my work for value` (2503.2, ep 108020627)
and `hank0123` (2428.5, ep 108023479). All three were checked afterwards: each appears in the
existing corpus **only as an opponent**, never as a tape's own cut seat. The disjointness that
matters — one tape per team, and no team whose play we already replay — holds: **48 unique teams,
0 of them the cut seat of any existing tape, 0 episode-id collisions against all 772 known ids.**

## 2. Fidelity check — 48/48, byte-exact

Every episode was cut twice by `scripts/tape_opponent.py` (the same code that cut LIVE-C, TOPB2 and
NEXT30) and each cut is verified by replaying the recorded actions back over the recorded
pre-states:

* **drawn** tape → `artifacts/panel_opp/opponent_tape_<ep>/main.py` + `artifacts/tape_actions/<ep>.npz`
* **pinned-town** tape (`--with-town`) → `artifacts/panel_opp_town/opponent_tape_<ep>/main.py`
  + `artifacts/tape_actions_town/<ep>.npz`

| check | result |
|---|---|
| replays downloaded, last byte `}` | **48 / 48** (1.5 GB) |
| drawn cuts `verified` | **48 / 48** |
| pinned-town cuts `verified` | **48 / 48** |
| steps / acting | **719 / 716-717** on every tape |
| town unlocks recorded | **8** on every tape |
| refused by `build_set.py` | **0** |

`build_set.py` refuses any episode whose two verify lines are not both `verified`, whose package or
either npz is missing, or whose town schedule is empty. Per-episode logs: `S/band40/cut/<ep>.out`;
the `verify_drawn` / `verify_town` columns of `S/band40/teams.csv` carry the same two words.

Town registry: `S/band40/town_schedules.json` = the **current shared registry**
`S/band2100p/town_schedules.json` (582 rows — NEXT30 is already merged into it) **+ the 48 new rows
= 630**, with every prior row asserted byte-equal. The shared file was NOT rewritten (judge legs
were reading it); `S/band40/town_append.sh` folds the 48 rows in, with a backup, when the lock is
free. `run.sh` refuses to start if any id in the list is absent from the registry, because an
unregistered id would silently be played with a *drawn* town — the exact fidelity failure the set
exists to avoid.

The 48 pinned-town npz were also rsynced to the training host with `--ignore-existing`:
`user@remote-host:~/stage_hr/artifacts/tape_actions_town/` went **568 → 616** files, nothing
overwritten, so a flow212 launcher can reference them immediately.

**Reading.** The set works: 80/80 games played, both seats, every board pinned, no void rows, both
files at a 76.2 % game win rate against 2350-2650 opposition. On the *ordering* question the leg is
**level**: B - hr = +117 coins/board, t +0.33, one game won each way, one board flipped to hr. That
is a null, not a reversal — and it is the expected one. NEXT30 (2550-2750) read B - hr = +697,
t +1.93 with the within-band gradient +1,377 at 2550-2650 and +102 at 2650-2750; BAND40 continues
that gradient straight down (+251 at 2500-2650, +18 at 2350-2500). B's edge over hr lives **above**
~2550 and vanishes in the LIVE-C band, which is exactly the "indistinguishable on common support"
line from the ladder work. Nothing here disturbs the incumbent or the flow209/210 seed choice.

What the set now buys the judge: **40 fresh LIVEC42-class boards**. LIVEC42 (42) + BAND40 (40) = 82
band boards of the same class, comfortably past the 59 the §107 per-family reading needs for
|t| ≥ 2 on the band leg of the objective trade.

## 4. Adding BAND40 to an objective launcher as a w4 family

`S/flow211/launch_flow211.sh` already reads its extra rung family **from a file** (lines 331-352),
so BAND40 needs no launcher edit — only the two environment knobs:

    NEXT_IDS_FILE=/mnt/e/_work/kaggriculture3/S/band40/ids.txt \
    NEXT_W_VALUE=4 \
    CUDA_VISIBLE_DEVICES=<gpu> nohup bash ~/launch_flow212.sh &

The loop then emits, for each of the 40 ids, exactly these two token forms (the same ones the
flow211 NEXT rungs use, with the weight changed from `10.2` to `4`):

    # appended to the --tape-actions comma list, one per id:
    ,artifacts/tape_actions_town/<id>.npz

    # one flag per id, appended to the argv:
    --rung-weight tape_act_<id>=4

i.e. for the first three BAND40 ids:

    --tape-actions <...166 inherited...>,artifacts/tape_actions_town/108016536.npz,artifacts/tape_actions_town/108018439.npz,artifacts/tape_actions_town/108018647.npz,<...37 more...>
    --rung-weight tape_act_108016536=4 --rung-weight tape_act_108018439=4 --rung-weight tape_act_108018647=4 ...

The launcher's own guards do the rest for free: it refuses if any
`artifacts/tape_actions_town/<id>.npz` is missing on the host (they are there — §2), and it refuses
if an id duplicates one of the 166 inherited rungs (none can — the ids are disjoint by
construction, §1).

**One thing must change in the launcher file itself**: the pinned-rung budget.

    N_PINNED = 166 + 40 = 206 > 198  →  "REFUSED: 206 pinned rungs against --episodes 200"

So `--episodes` has to be raised to **≥ 208** in the same edit (the pinned block is never truncated,
so the run would otherwise silently spend `N_PINNED + 2` episodes/gen), or the 30 NEXT30 ids
dropped from the family so that 166 + 40 fits a raised budget on its own. Raising `--episodes` is
the honest option: at 208 the generation cost goes up ~4 % over flow211's 200.

Objective mass, if BAND40 goes in at w4 alongside flow211's blocks (raw rung weight = count ×
weight): BAND40 40 × 4 = 160, against NEXT30 30 × 10.2 = 306, the 20 top-ten rungs at 4 = 80, and
LIVE-C 1-42 at 4 = 168. A **band-only** flow212 (the §110 arm) instead zeroes the non-band families
and keeps BAND40 + LIVEC42 + NEXT30-lower as the whole objective; the token forms above are
unchanged either way.
