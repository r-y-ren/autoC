**최신 등록 권한 변경:** 연구·검증·패배 분석은 계속하되 새 로컬 등록과 Kaggle 제출은 사용자가 직접 하거나 해당 후보/작업을 명시 승인한 뒤에만 수행한다. 이전 자동 제출 허용은 대체됐다. 결과·정확 tar를 먼저 준비하고, 검증 기록 편입은 적격 등록이 실제 존재한 뒤 수행한다.

소유자는 c462/c465 임시 확인을 승인한 뒤, 앞으로는 **예상 완료 시각 부근에 첫 확인, 이후 10분 간격**을 요청했다. 아래의 예약 자동화 금지와 활성 도구 대기 지시는 이 완료 확인 방식에 한해 대체한다. 광범위한 정기 연구 알람은 복원하지 않는다.

1. 경기와 후처리는 여전히 단일 OS 체인에서 수행한다. 완료된 비슷한 캠페인의 처리량 또는 저장된 ETA로 남은 전체 단계 시간을 추정하고 회계·후처리 여유를 더한다. 실행 중 모델이 반복 조회해 ETA를 갱신하지 않는다.

3. 각 확인은 최종 결과/오류 파일과 실제 프로세스를 한 번만 읽는다. 정상 실행 중이면 조용히 종료한다. 완료/실제 오류/이미 리뷰됨이면 알람을 삭제하고 저장 결과를 재사용해 리뷰·복구·승인된 후속 연구를 진행한다. 사용자가 먼저 완료를 알려도 동일하다.
4. 최종 리뷰와 기존 기준에 따른 로컬 등록 후 `tools/import_validation_league.py apply SCREEN CONFIRM`을 한 번 실행하고 `verify`한다. 여러 경기 기록·중복 제거·BT 갱신·영수증을 공통 코드가 처리한다. 기록 편입을 위해 미검증 후보를 등록하지 않으며, 승패 전체를 가져온다. 사용법은 [연구 도구 안내](research-tools.ko.md)를 따른다.

앱 재개 메시지의 독립 실행 경로가 검증되지 않은 이 환경에서는 이 임시 확인이 현재 승인된 재개 경로다. CPU 작업 자체가 모델을 호출하지 않지만 예약 확인과 이후 리뷰는 토큰을 쓴다.

## 실제 확인된 한계 — 기존 구현 안내보다 우선

c447에서는 경기 완료가 14:23:30 UTC, 로컬 중단 감지가 14:26:53, 도구 스크립트의 후속 메시지 전달이 14:33:50이었다. 후처리도 14:33에 시작했다. 따라서 응답을 종료한 뒤 yielded `functions.exec`가 곧바로 다음 도구를 호출해 주 작업을 깨운다는 이전 보장은 철회한다. 정확한 앱 내부 지연 원인은 확정하지 않았으며, 로컬 감지기 정상 작동과 앱 재개 연결의 즉시 실행은 별개다.

경기·집계·후처리는 하나의 OS 프로세스에서 끝까지 연결한다(`state/c447/formal/drive.py`). 독립적으로 실행되는 앱 재개 경로를 확인하기 전에는 **응답을 먼저 종료하지 않고 한 도구 실행 내부에서 CPU 완료를 기다린 후 직접 결과를 받아 리뷰**한다. 반복 모델 progress 조회는 하지 않는다. 대기 도구가 반환돼 모델이 호출되면 그 문맥 처리 비용은 있을 수 있으므로 전 과정 토큰 0이라고 약속하지 않는다.

공식 app-server의 CLI proxy 경로도 확인했으나 이 환경의 기본 control socket 연결은 실패했다. 앱을 재시작하거나 별도 모델 세션을 만들지 않았다. 독립 전송 경로가 실제 확인되기 전에는 아래 callback 설계와 c447 예시를 작동이 보장된 설정으로 사용하지 않는다.

## 기본 실행 순서

1. HANDOFF START HERE, 실제 프로세스, 완료 산출물, 기존 완료 콜백부터 확인한다. 이미 실행 중인 캠페인이나 대기 콜백을 중복 시작하지 않는다.
2. 동결된 경기 실행 → 사전 기준 판정 → 조건부 확인 검증 → 선택 실행·회계 검사 → 완료/실패 파일 작성을 하나의 프로세스 또는 도구 스크립트로 연결한다. 완료 작업은 재사용하며 중간 성적으로 튜닝하지 않는다.
3. 현재 연구를 맡은 작업 ID를 도구/환경에서 확인한다. 이전 문서의 작업 ID, PID, 도구 cell ID를 새 세션에 복사하지 않는다. 기존 실행을 인계받을 때도 실제 소유 세션과 유효한 콜백을 먼저 확인한다.
4. 실행마다 고유 event ID와 최종 산출물 경로를 고정한다. 단일 대기 프로세스/도구 스크립트가 완료 또는 실행 중단을 확인하고, 검증된 작업에 `send_message_to_thread`를 한 번 호출하도록 연결한다. 메시지에는 event ID·결과 경로·해시·다음 판정 범위만 넣는다. 모델/사고 강도는 현재 설정을 유지한다.
5. 콜백 프로세스의 시작과 실제 도구 연결을 확인한 뒤 현재 모델 응답을 끝낸다. `wait`/`sleep`/`progress`를 모델이 주기적으로 호출하지 않는다. 대기가 필요하면 도구 스크립트 내부에서 처리하며, 원시 로그를 모델에 계속 출력하지 않는다.
6. 완료 메시지를 받은 세션은 event 처리 여부를 확인하고 리뷰 소유권을 기록한다. 최종 통계·소스 신원·실행·회계를 검토하고, HANDOFF에 판정을 남긴 뒤 승인된 다음 연구를 이어간다. 다음 긴 실행에도 같은 완료 콜백을 연결한다. 사용자 입력을 이유 없이 기다리지 않는다.

## 중복 방지와 중단 복구

- 전달 상태는 `armed → dispatching → sent`로 기록하고, 응답이 불명확하면 `uncertain`으로 남긴다. 수신 리뷰 완료는 별도 `reviewed` 기록으로 남긴다. `sent`는 리뷰 완료를 뜻하지 않는다.
- `dispatching/uncertain` 상태에서 자동 재전송하지 않는다. 대상 작업에 event가 도착했는지 먼저 확인한다. 이벤트 파일·전달 잠금·리뷰 소유 기록을 함께 사용해 중복 실행을 막는다. 장애 상황까지 정확히 한 번 전달된다고 보장하지 않는다.
- 정상 완료 외에도 실행 실패, 완료 파일 없이 프로세스 종료, 마감 도달을 구분해 한 번 전달한다. PID 종료 직후에는 후처리 프로세스로 넘어가는 구간인지 확인한다.
- 저장된 `armed` JSON만으로 연결이 살아 있다고 판단하지 않는다. 연구 프로세스, 대기 프로세스, 도구 오케스트레이션의 실제 상태를 확인한다. 도구 실행 자체가 끊겼다면 로컬 Python이 살아 있어도 앱 후속 메시지를 보낼 수 없을 수 있다.
- PC/Codex 종료·절전·도구 세션 손실 뒤 자동 복구를 보장하지 않는다. 다음 세션이 기존 결과와 프로세스를 확인한 뒤 필요한 연결만 복구한다. 완료 경기를 다시 실행하지 않는다.
- 사용자가 연구 중지를 요청하거나 마감에 도달하면 새로운 연구를 시작하지 않는다. 미전달 콜백을 취소하고, 뒤늦게 도착한 이벤트도 최신 중지 지시를 따른다.

## 비용과 기존 승인 범위

대기 중 모델 호출을 없애는 방식이다. 완료 후 문맥 읽기·결과 리뷰·설계·구현은 토큰을 사용하며 계정 전체 사용량에는 다른 작업도 포함된다. 단순히 CPU 작업이라는 이유로 전체 작업이 무료라고 설명하지 않는다.

Astra가 직접 작업하며 Sol/하위 에이전트는 사용하지 않는다. 상단 최신 지시에 따른 ETA 이후 임시 확인만 사용하고 광범위한 정기 연구 알람은 복원하지 않는다. 동결 코드·계약·보호 blind·단일 캠페인·제출 검증 기준은 그대로 유지한다. 연구 중 League 대결이 켜지면 소유자 승인에 따라 정상 중지하고 서버·자동 수집·최신 설정을 보존한다.

## 현재 구현을 재사용할 때

- 로컬 완료 감지 예: `state/c447/completion_event.py`. c447 전용 경로·마감·event를 갖는 예시이므로 다음 실험에 무수정 실행하지 않는다.
- 과거 도구 연결 예: `state/c447/completion-callback.exec.js`. 지연이 관측된 구현이며 응답 종료 후 자동 재개의 확정된 해법이 아니다. `functions.exec` 런타임용이고 Node/Python에서 실행하는 파일이 아니다. **Python 감지기만 실행해서는 앱이 자동으로 재개되지 않는다.**
- 상태 파일: `state/c447/completion-callback.json`, `completion-event.json`, `completion-waiter-pid.json`. 현재 ID와 경로는 HANDOFF를 따른다. 기존 c447 콜백이 살아 있으면 예시를 다시 실행하지 않는다.
- 새 세션은 최소한 event ID, 대상 작업, 연구/대기 프로세스 식별자, 결과·전달·리뷰 기록 경로를 HANDOFF에 남긴다. 실제 연결이 미지원이거나 끊겼으면 자동 재개가 설정됐다고 주장하지 않는다.

## 2026-09-28 KST 추가 — OS 완료 알림과 기존 임시 확인 병행

소유자는 기존 ETA 이후10분 임시 확인을 유지하면서 Windows 완료 알림을 요청했다. 사용자 완료 통보가 먼저 오면 저장 결과로 즉시 리뷰하고 해당 임시 확인을 삭제한다. 통보가 없으면 기존 임시 확인이 복구 경로로 남는다.

새 긴 체인의 실제 coordinator PID를 확인한 다음 `tools/notify-research-completion.ps1 -StateDir <최종결과디렉터리> -Label <단계> -OwnerPid <실제PID>`를 `powershell.exe -NoProfile -STA -ExecutionPolicy Bypass -File`로 숨김 실행한다. Start-Process에는 -WindowStyle Hidden을 사용한다. 기존 run-validation.ps1/v2/v3의 NotifyIcon+sound 방식을 재사용하는 최소 공통 확장으로 동결 runner는 수정하지 않는다. OS process-exit 대기 뒤 completion-ready/execution-error를 확인해 단계별1회 알린다. campaign 실행·모델호출·새 등록/제출은 하지 않는다. 알림은 실행종료이며 성능채택을 의미하지 않는다.

`windows-notifier-process.json`과 실제PID로 대기등록을 확인한다. `windows-notification.json`의 requested는 API요청, shown은 Windows BalloonTipShown 이벤트를 뜻하며 사용자가 읽었다는 증거는 아니다. 디렉터리별lock/receipt로 중복을 막고 오류는 windows-notification-error.json에 기록한다. 임시앱확인/리뷰는 여전히 토큰을 사용한다. PowerShell5 한글표시를 위해 스크립트는 UTF-8 BOM으로 보존한다. 자체알림이 있는 canonical runner와 보조 notifier를 중복 사용하지 않는다.
