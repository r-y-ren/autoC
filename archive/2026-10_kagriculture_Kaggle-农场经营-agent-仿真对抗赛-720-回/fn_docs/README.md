# Kaggriculture 农场竞赛作战系统

> 状态：v1（2026-09-21 阶段三裁决后回写：矛盾 8 处修正、补 10 项未提及行为；裁决记录见 requirements.md 变更记录）。本文为项目用户向总览，此后仅在需求变更时经 grill 更新。

## 这个工作区是什么

一套参加 Kaggle「Kaggriculture」农场经营对抗赛的完整作战系统。比赛规则一句话：两名选手各自经营一座农场，模拟 30 天（共 720 个回合），结束时钱多的一方赢；全程在一个只按胜负计分的天梯上排位，2026-09-30 终交。【出处：strategy.md §一（2026-08-28 官方直抓）】

工作区里装的不只是一个参赛程序，而是四样东西：

1. **参赛 bot 本体**——线上提交的选手程序，每个回合决定工人干什么活、买卖什么；
2. **一套离线考试系统**——本地对局评估、自动检查关、以及一台能逐位复算官方对局的"复算器"；
3. **一套线上作战记录与复盘系统**——提交台账、官方回放拉取、对手画像与败局取证；
4. **战役治理文件**——蓝图（里程碑与验收清单）、指标、日志。

【出处：blueprint.md scope；CODEMAP.md 八大类】

## 工作流程

### A. 一局比赛内，bot 是怎么决策的

比赛按回合进行，720 个回合=模拟 30 天。bot 的工作循环：

1. **装载**：线上环境只认一个提交包。`main.py` 是个薄装载器，按固定顺序把**十个**功能模块和规划器装进内存（自包含多模块包，经确定性打包成提交件——不是单文件）。装载窗口内必须立刻导入规划器——否则回合开始后导入通道已被官方环境关闭，规划器会全程沉默（这是 2026-09-19 法证定位的"零接合"事故根因，已修复并有常驻测试把守）。【出处：CODEMAP A；session-findings 工程#1】
2. **每个回合的决策四层**：先"看"——估计对手的供给与资金状况（观察层）；再"定方向"——当前该主攻种地、养畜还是扩张（宏观策略层）；再"派活"——把活计按死线紧急度打包（任务层）；再"排路线"——给每个工人算一条走完所有活计的路线并沿线执行（求解与执行层）。【出处：CODEMAP A；docs/worker_route_scheduler_design.md】
3. **每天一次"黎明规划"**：每天开始时有一个规划点。bot 用内置的官方引擎复制品（"数字孪生"）把"今天起若执行计划 A/B/C……各自会怎样"完整模拟到赛季结束，每种计划对着几种不同风格的假想对手各推演一遍，选最稳的计划注入当天的执行层。模拟出错或超限就当场退回纯反应式执行（三道保险丝）。另有一套"波次日历剧本"（整季日程表打法）作为规划器的候选之一——它不是纯休眠，规划器每天都会把它排进比较集。【出处：blueprint m6/m7；track-B-digital-twin-planner.md；CODEMAP A wave】
4. **市场层**：每天清晨决定卖什么、卖多少批（吸收表×价格曲线投影），以及买畜、外购饲料的门控；另有对账件核对"计划卖单 vs 引擎实际成交"。【出处：CODEMAP A market.py；market_ledger/sell_plan_reconciliation】

### B. 一轮开发迭代是怎么走的（主循环）

从改代码到知道"线上到底变强了没有"的完整闭环：

1. 改候选（bot 的策略参数或代码）；
2. 过本地门：全量测试、冒烟自打、身份链校验、确定性打包复验；
3. 过发射门：**不看本地涨分**——本地对局数字只算"灾难诊断"，永不构成"该提交了"的证据（本地连涨三代 +28.8% 线上反输旧版的反例已钉死此纪律）；
4. 人工提交到 Kaggle（每日至多 5 次）；
5. 提交后**必须**用官方通道把公开对局回放拉回来、写入采样台账（本地自对局顶替会被门禁直接拒绝）；
6. 对回放做画像与败局取证（钱曲线、畜群轨迹、雇佣强度、分歧日定位），结论入档；
7. 复盘裁决：下一刀参数必须引用这些官方局，而不是本地百分比。

【出处：online_probe_sop.md 全文；final_sprint_plan Q2；session-findings】

### C. 终局程序（最后两周的收口）

天梯只跟踪每队**最近 2 次**提交，且只有这两次参与最终定榜——所以终局序列要倒排。当前程序：终榜对已就位（一份我方最佳原创 v14.2 + 一份 v48 公开衍生版，后者已翻倍我方全家族线上天花板），现在处于零提交静默期，09-29/30 最后提交我方最佳原创收口。【出处：JOURNAL 2026-09-21 round-26；session-findings 工程#9、情报#3】

### D. 战役治理流程

蓝图定义里程碑与验收清单，逐波交付。**实际治理现状（2026-09-21 诚实口径）**：全量自动验收链（/accept）自 09-01 起静默（09-19 增补的 m6/m7 无验收记录，蓝图 2 条文档类验收命令指向尚未生成的报告文件）；事实权威源是 **JOURNAL 详记 + git 提交 + metrics 分片**，根 metrics 由合并脚本从角色分片生成。【出处：acceptance/；requirements.md R17 留档】

## 名词小词典（平实版）

- **回合 / 天**：比赛的最小时间单位；720 回合=30 天，每天 24 回合，每天开始处即"黎明"。
- **席位（seat）**：一局里两个玩家的槽位（0 号/1 号）。评估必须说清我方坐哪号——"席位错位"就是把我方动作恒注入 0 号位的评估缺陷，坐 1 号位的局数字全错。
- **孪生（数字孪生）**：官方游戏引擎的 1:1 离线复制品，能从回放中途接手并算出与官方完全一致的后续。
- **快照反例**：特意构造的用例，让旧代码失败、新代码通过——用来证明缺陷真的修掉了。
- **身份链**：用文件哈希给每个候选版本发"身份证"，保证评测、冻结、线上提交说的是同一个东西。
- **holdout**：一次性独立考卷：全新随机种子上跑一遍，结果无论好坏如实入档，禁止重跑或换种子。
- **门禁**：自动检查关，不过不许进行下一步（提交、换参、进下一波）。
- **fail-open / fail-closed**：失败时的两种姿态——规划器出错就退回安全打法（open，比赛不能停）；台账校验不过就直接拒绝（closed，宁停不错）。
- **旋钮**：可调参数。总开关关掉时行为与旧版逐字节一致，是"加新东西不惊动旧东西"的安全模式。
- **快照/黄金哈希**：把"正确行为"的输出指纹存下来，改动后比对指纹不变，即行为未变。
- **最小可复算集**：保证新机器克隆代码后能跑通核心检查的最小数据包（金手指纹、关键回放、种子定义等）——本轮重构将把它们从"只在主力机"转入库。
