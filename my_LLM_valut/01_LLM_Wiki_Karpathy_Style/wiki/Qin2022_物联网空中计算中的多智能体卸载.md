# Qin2022_物联网空中计算中的多智能体卸载

## 单行摘要
论文在 LEO 卫星移动边缘计算场景中构建 UE-LEO-Cloud 三层空中计算架构，并以 centralized training / distributed execution 的多智能体 actor-critic 联合优化本地、星上与云端卸载及传输功率，降低 IoT 任务的时延与能耗成本。

## 题目驱动研究框架
- 研究场景：复杂地形、海洋、灾区等地面基础设施稀缺区域中的 LEO-SMEC 任务处理。
- 研究对象：IoT 终端、LEO 卫星 MEC 服务器、远端云服务器。
- 核心问题：星上算力有限且卫星链路带宽/时延受限，单纯本地计算或全量上云都不理想。
- 标题承诺的方法：以 MARL aid computation offloading 统一处理空中计算中的分布式卸载决策。
- 期望效果：兼顾任务时延与能耗，在大规模分布式终端条件下维持较好收敛与协同效果。

## Algorithm Design 快照
论文不是把卫星当成普通远端服务器，而是明确提出三层 SMEC：UE、本地可见 LEO MEC、远端云。任务被拆成带依赖关系的子任务，终端需要在本地、卫星和云之间做离散卸载选择，并同时决定传输功率。由于完全中心化调度在大规模 LEO 网络中过于昂贵，作者采用云端集中 critic + 终端分布式 actor 的混合训练执行框架，让每个 UE 在仅依赖局部观测的情况下学习协同卸载。

## 图1系统框架草案
- Tier 1：多个 IoT UE，持续生成 DAG 型计算任务。
- Tier 2：多颗 LEO 卫星，搭载 MEC 服务器。
- Tier 3：远端云服务器，提供更强算力但更长回传路径。
- 决策变量：本地/卫星/云卸载选择，发往卫星与云的传输功率。
- 优化目标：联合最小化时延与能耗成本。
- 学习结构：云侧 centralized critic 汇聚全局状态，UE 侧 actor 仅依赖局部观测独立执行。

## System Model
### 1. 三层 SMEC 架构
- 系统由多个 UE、多个 LEO 卫星和多个云服务器组成。
- 每个 UE 可以本地执行、卸载至最近可用 LEO，或继续上送云端。
- 论文关注小时间尺度下的卸载决策，因此把卫星视作准静态，不处理卫星切换。

### 2. DAG 子任务依赖
- 单个应用任务被拆成有时序与数据依赖的子任务序列。
- 每个子任务包含数据规模、CPU 周期需求和最大时延约束。
- 这使得卸载不再是单个独立任务的二元选择，而是依赖结构下的多阶段决策。

### 3. 通信与功率模型
- UE 到卫星、卫星到云端的链路速率都显式进入时延和能耗计算。
- 卸载变量与传输功率联合决定总成本，因此资源控制与卸载决策是绑定的。

## Algorithm Design 详解
### 1. CTDE 多智能体卸载
- 每个 UE 部署 actor，依据本地观测独立选择卸载位置与功率策略。
- 云端部署 centralized critic，用全局状态与联合动作评价各终端决策。
- 这种结构既保留分布式执行，又缓解纯独立学习的非收敛问题。

### 2. 策略估计与协同
- 论文进一步估计其他 agent 的策略分布，减少隐私约束下的协同困难。
- 这类设计对后续星空地分布式卸载研究很有启发价值。

### 3. 实验结论
- 在含 `3` 颗 LEO 和 `9` 个 UE 的代表拓扑上，算法约在 `2k` 迭代左右收敛。
- 与 DDPG、Local Execution、Random Action 相比，所提方法在总成本、协同稳定性与公平性方面都更优。
- 这篇论文的重要性在于，它把“空中计算”真正落到了可学习的三层卸载框架上。

## Introduction 写作素材
- LEO 网络提供了比地面网络更广的可达性，但其大传播时延和有限星上资源使任务处理仍然困难。
- 因而真正的问题不只是“能不能连上卫星”，而是“连接之后任务应该在本地、星上还是云端完成”。
- 这篇论文适合支撑“空中计算需要把通信覆盖与计算调度共同建模”的写作判断。

## Related Work 写作素材
- 早期卫星卸载更多关注资源分配或纯集中式调度。
- 多层卸载已有研究，但往往不强调终端侧分布式执行与协同学习。
- 本文把 CTDE 型 MARL 引入三层 SMEC，凸显了空中计算场景下的协作学习价值。
