# 分析 05 —— 纯 v48 协调规划机制深读：为什么"参考它的模块算法"救不了计划层（2026-09-23）
> 用户问："既然都是规则策略，为何不能直接参考纯 v48 对应模块的算法？"数据：results/2026-09-23-v48-coordination-deepread/（详版+模块+磁带）。

## 一、v48 协调规划的真相
1. **磁带不是包内算法生成的**：v21_route_memory_search 仅 296B 回放器。6 磁带=**1 骨干走位+3 异家真轨迹续篇**（Kaileh57@88/taiseiu@120/v44 验证续篇）**+2 市场编辑版**（farmer 流与 default 逐字相同，仅市场单被改）；嵌缀树分叉与路由决策步精确对齐。
2. **在线协调 <5%**：单位动作 716/688 步全离线；在线=1 路由锁存（事件 88/120/153/216，"晚重评跳入已发散后缀"故每席一次）+1 面包分支+1 克隆否决+抢卖窗（零和时移）+槽位排序+718 一步。无再规划。
3. **生成管线不在包里**：挖掘/medoid/编辑/holdout 全在作者离线环境——包内只有回放器与反射件。

## 二、对用户问题的直接回答
混合件已是"参考模块算法"的极限（=v48 字节+我方层）；R9 失败在**计划层内容**：v48 模块是执行器/反射件，**不含生成一季协调计划的算法**。我们用**建模生成**（M0+M4→排程）替换了它的**搜索生成**（轨迹挖掘+holdout 选择）——R9 根因细化：**计划层必须搜索生成**。外证：island-ga 同计划 147.3k vs 重调度 72.8k；94% 座位 turn24 前同开局="脚本大陆"；2945 同构 0-36=磁带质量与选择压才是分野。
