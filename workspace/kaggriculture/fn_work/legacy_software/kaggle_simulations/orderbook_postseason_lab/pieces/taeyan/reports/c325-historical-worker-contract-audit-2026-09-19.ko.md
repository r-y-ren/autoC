# c325 — c176 부모 대조 복구·일손 번호 충돌 감사

판정: **과거 실패에 실제 실행 결함이 있었지만, 단일 수리 후에도 부모보다 크게 약하다. 확대 평가·승격·제출 없음.** 현재 개발 기준선 c312 v9 유지. 보호 blind 7240–7255 미사용.

## 이력 정정과 재시도 근거

가까운 선행은 c176(기존 밀 타일의 토마토 전환+전용 일손), c177–180(기존 딸기 레인 전환), c313(수확 달력), c321–323(생산 일정 생성·검색)이다. c176 보고서는 implemented_unvalidated였지만 실제 4스모크가 있었다. 이전 c312/c313 이력 정리의 “부모 대조 없음”은 검색 범위가 좁아 잘못된 설명이었다.

- 후보: `o_results/c176_smoke_c150.json`.
- 부모: `o_results/strat/o199c/tomato__c150.json`의 72행 중 같은 7015/7056 양좌석 4행.
- 부모/overlay/후보 원본 SHA는 c176 원래 manifest와 일치.
- 재현 QA20: 과거 최종 현금 8/8, native/fast 관측·행동·최종 상태 8/8, c176 OFF와 부모 4/4 동일. 최대 결정 0.143초, 관측 변조 없음.
- 과거 원자료에는 행동 해시가 없어 **역사 행동 스트림 동일성**까지 주장하지 않는다. 모드/OFF 전체 스트림 검증은 이번 재현끼리의 비교다.

현재 엔진에서 재현된 c176−부모:

- 7015: own −15,653 / 상대 +11,022 / margin −26,675.
- 7056: own −8,119 / 상대 +8,935 / margin −17,054.

양좌석 결과가 같아도 독립 세계는 2개다. 현대 상위권 검증이 아니다.

## 원장과 실제 운영

기존 `state/c313/run_mechanism.py` 및 `o_tools/pair_trace.py` 재사용. 부모/후보 8재생 모두 QA의 양측 행동 해시·현금 일치, 양측 전체 현금 회계 잔차 0. 읽기 전용 부모 명령·전용 일손·일말 타일 계측을 추가했다.

c176은 토마토를 기존 운영에 단순 추가하지 않는다. 부모 V219의 SE 토지·토마토 투자를 막고 기존 밀 타일 10개를 대체한다.

- 토마토 실수확: 부모 80/78u → c176 31/31u. 과거 telemetry의 추가 판매 요청 24u는 총수확량이 아니다.
- 토마토 매출 Δ: −8,125 / −5,636.
- 밀 수확 Δ: −151 / −94u. 밀 구매 지출 Δ: +3,710 / +1,650. `feed_wheat`는 전체 밀 구매 분류이며 전액을 직접 사료 소비로 단정하지 않는다.
- 토지 지출 −4,000, 고용 지출 +377. 토마토 씨앗 지출 Δ는 0: 부모도 토마토를 샀다.
- 10타일 파종은 확인됐지만 일부 날 1–4타일에 물을 주지 못했다. 전용 일손의 이동은 372/369명령, WATER는 48/46명령. 부모도 전환 타일을 계속 방문하므로 이 수치만으로 작업 기여를 분리할 수 없다.
- **구체적 결함:** 7015의 d23–26에서 c176이 먼저 고용한 일손 번호를 부모가 나중에 사용한다. 부모 비PASS 명령과 소유권이 겹친 경우 129회, 그중 실제 명령이 달라진 경우 **116회**다. 최초 설명의 “129명령 덮음”은 번호 중복 횟수이며 명령 차이 횟수와 구분한다. 7056은 이 충돌 0회인데도 큰 손실이다.

후반 상점 경로가 정책에 따라 달라진다. 위 수익 차이는 native 전체 정책 차이이며, 회계 잔차 0이 개별 기전의 인과 분해를 보증하지 않는다.

## 단일 수리와 중단

`state/c325/worker_reservation.py`: 현재 선택된 자기 경로와 후반 fallback 경로에서 당일 사용할 일손 번호를 미리 확인하고, 부모가 그 번호들까지 확보한 뒤에만 추가 일손을 고용한다. 자기 코드의 예정 동작만 참고하며 미래 상점·상대 신원·시드는 쓰지 않는다. 기존 물량·분기 조건은 변경하지 않았다. 새로운 경로 전환/부모 overlay 전체에 대한 일반 소유권 보증은 아니다.

사전 확대 조건: 두 개발 세계 모두 원부모 대비 own·margin 양수. 단일 수리 native/fast QA8, 4쌍 전체 스트림 동일. 읽기 전용 추가 원장4도 QA 행동·현금 재현, 관찰된 번호 충돌은 모두 0.

- 7015: c176 대비 own +6,671 / margin +12,140. **원부모 대비 own −8,982 / margin −14,535**.
- 7056: c176과 양측 행동 해시·현금 동일. **원부모 대비 own −8,119 / margin −17,054**.
- 수리 후 토마토 수확은 양세계 31u 그대로. 7015의 밀은 400→458u지만 부모 551u에는 못 미친다.
- 따라서 확대 조건 FAIL. 일손 수·타일 수·가격 조건 추가 탐색, 다른 부모로 같은 전환 이식, 독립 확인/final은 실행하지 않았다.

첫 수리 번들은 파일 끝에 entrypoint를 재배치하지 않아 legacy loader가 추가 helper를 agent로 고르는 QA 오류가 났다. 첫 파일/계약/로그를 보존하고 `repaired_v2.py`에 기존 프로젝트 방식인 `agent = globals().pop("agent")`만 붙여 별도 QA를 수행했다. 실패 QA는 성능 표본에서 제외한다. 당시 첫 스크립트가 assert 전에 개별 결과를 저장하지 않아 실패 실행의 각 행은 남지 않았으며 실패 로그와 계약만 있다. v2부터 저장 후 assert하도록 변경했다.

## 재사용할 교훈

1. 과거 보고서의 미검증/미실행 표시는 실제 결과 파일과 별도 부모 폴더까지 대조한다.
2. 기존 계획 위 추가 고용은 현재 일손 수만 확인해서는 안전하지 않다. 같은 날 늦게 생성되는 부모의 논리 번호도 보호해야 한다.
3. 대체 정책에서 “토지 비용 절감”은 포기한 기존 토마토 생산·밀 생산까지 포함해 비교한다.
4. 오류 수정으로 실패 정책이 개선돼도 강한 기준선보다 약하면 승격 근거가 아니다. 버그가 하나 있었다고 과거 모든 음수 결과를 무효화하지 않는다.

원자료: `state/c325/{historical_result,ledger_result,repair_result,repair_service_result}.json`. 동결 c176/부모·과거 결과 파일은 변경하지 않았다.
