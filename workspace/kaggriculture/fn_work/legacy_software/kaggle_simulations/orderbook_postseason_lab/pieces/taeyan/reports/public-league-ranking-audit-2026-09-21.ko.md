## 대진 구성에 대한 실제 순위 민감도

저장 승패를 바꾸지 않고 같은 BT 목적함수로 집계 범위만 바꿨다.

- 전체: c365 → c358 → Master Engine V3.
- 현재 상위10 사이 494경기만: c365 → c358 → Moon Counts Melons.
- 현재 상위20 사이 1,482경기만: **Moon Counts Melons → c358 → c365**.
- v2 배포 공지 이후 10,195경기만: c365 → Local Best 2026-09-20 → More Wheat, Smarter Sales(agent142).

부분집합의 점수 절댓값은 서로 비교하면 안 된다. 위 순서 변경도 다른 모델이 실제 최강임을 입증하지 않는다. 사후 선정된 풀이고 새 agent들의 표본이 얇다. 확인되는 것은 **1위 판단이 평가 상대·기간에 민감하다**는 사실이다. v2 이후만 자르는 것도 실행 차이뿐 아니라 대진과 표본 수를 함께 바꾸므로 'v1이 틀렸다'는 실험이 아니다.

현재 매칭은 `schedule_matches`에서 경기 수 부족을 먼저, 덜 만난 조합을 다음으로, BT 거리를 이후에 본다. 100명 상위끼리 자동 완전리그를 하는 것도, 공식처럼 유사 실력만 우선하는 것도 아니다. 이것은 넓은 후보 탐색에는 유용하지만 근소한 상위 순서를 빠르게 확정하는 목적에는 비효율적이다. 32경기 후 상위100 밖으로 밀린 agent는 일반 편성에서 오래 제외될 수 있다. 코드 신원이 서로 다른 과거 버전도 상대에 남는다(현재 eligible 중 최신 alias가 없는 agent 12개). 계보가 많은 전략의 비중이 커질 수 있으므로 미세 변경을 삭제하지 않으면서 별도의 계보 가중 민감도를 봐야 한다.

## 코드에서 확인한 보완점

### 1. 결과 정규화가 잘못된 seed를 다시 유효하게 만들 수 있음

`championship_league.run_match`는 실제 엔진 seed가 예정 seed인지 검사하지만, `normalize_public_league_result`는 valid=False의 원인이 seed 불일치여도 나머지 완주 조건만 맞으면 valid=True로 바꾼다. 저장 완료 결과의 메모리 복사본에서 resolved_seed만 +1하고 valid=False로 설정한 최소 진단이 이를 재현했다. **현재 완료 25,344건에서는 실제 seed 불일치 0**이므로 기존 결과 오염 증거는 아니다. 타이밍 경고 복구 때 신원·시드·완주 검사를 모두 보존하도록 고쳐야 할 방어 결함이다.

### 2. 양측 정책의 프로세스가 분리되지 않음

한 경기 subprocess에서 두 Python 정책을 호출하므로 `sys.modules`, 난수 등 프로세스 전역 상태를 공유한다. Docker 경기 역시 한 컨테이너의 한 match process에서 두 정책을 실행한다. 공식 source loader를 그대로 사용해도 두 제출을 격리해 주지는 않는다.

서로 다른 폴더에 동일 이름 helper를 두고 각각 A/B를 반환하게 한 최소 loader 진단에서 실제 반환은 **A/A**였다. 즉 이름이 겹치는 일반 import가 상대 모듈로 연결될 수 있는 실행 결함은 재현했다. **현재 상위 순위가 이 결함으로 오염됐다고 입증한 것은 아니다.** 정적 검사에서 다른 내용의 같은 모듈명 후보는 153–161(4경기), 153–198(8경기)이었지만 이 계보는 sibling을 명시적으로 다시 로드한다. 153/198의 retained router/planner/imported function 경로를 검사한 결과 각자 자기 파일을 가리켰다. 정적 이름 중복만으로 해당 경기를 무효화하면 안 된다. 실제 영향 확인과 독립 프로세스 실행이 후속 과제다.

### 3. 계약 변경 전후 기록과 소량의 동일 경기 재집계

현재 순위는 11개 실행 계약 해시의 complete를 함께 쓴다. 해시에는 collector/UI를 포함한 public_league.py 전체도 들어가므로 해시 차이=게임 규칙 차이는 아니다. 의미상 호환되는 결과는 재사용할 수 있지만 호환 여부를 판정하는 구분이 필요하다.

동일 artifact pair·seed·좌석 중복 키가 106개이며, 최신 1건씩만 남기면 25,344→25,238이다. 중복의 현금·승패 불일치 0. 중복을 제거해 재계산해도 상위 순서는 같고 c365는 2633.46→2632.43, c358은 2607.40→2606.70이다. **현재 1위를 만드는 주원인은 아니지만 독립 표본으로 중복 집계하면 안 된다.**

### 4. 강도와 실행 신뢰성이 분리되지 않은 표시

실제 agent 오류/timeout 경기도 invalid로 승패에서 제외되고 반복 코드 실패는 quarantine된다. 로컬 자산 누락·플랫폼 문제를 패배로 넣으면 안 되지만, 진짜 정책 실패 위험도 완주한 경기의 BT만으로는 드러나지 않는다. '정상 완주 시 강도'와 agent 귀속 실패율을 함께 봐야 한다. 이번에는 317 invalid 전체의 원인을 다시 판정하지 않았으며 [같은 날 격리 재감사](public-league-current-quarantine-2026-09-21.ko.md)를 재사용한다.

또한 artifact 전체는 이번 현재시점 해시 검사를 통과했지만 매 경기 runner의 직접 신원 확인은 main.py에 한정된다. sidecar까지 실행 전후 확인해야 재현성 계약이 완전하다. OS/라이브러리/CPU와 비공개 상대 풀도 공식 환경과 같지 않다.

## 권장 운영 방식

1. **기존 연속 리그는 탐색용으로 유지.** 자동 수집, exact 중복 통합, 신규 우선 편성, 상위100 관리는 유용하다. 최상위 근접 경쟁자끼리의 대전과 archived 재진입 탐색에 별도 비중을 주면 효율을 높일 수 있다.
2. **최종 후보 선발은 별도 상위권 공통 패널.** 실행 결함을 보완한 뒤 현재 상위10 안팎과 새 유력 후보를 동결하고, 모든 후보가 동일한 새로운 세계와 양좌석에서 공통 상대를 만나게 한다. 상대 동일 가중 집계와 계보 가중 민감도, 직접 대전 행렬을 같이 본다. 미세 수정은 중복으로 없애지 않는다.
3. **500판을 충분성 기준으로 삼지 않음.** 중요한 상대별 독립 세계 수·승점 차·seed 단위 구간이 핵심이다. 평가 전 표본/판정 규칙을 고정한다. 결과를 보며 '유의할 때까지' 반복하려면 순차검정과 다중 비교 보정이 필요하다. 탐색에서 골라낸 1위를 같은 데이터로 확정하지 않는다.
4. **제출은 로컬 증거와 별도로 판단.** 공개풀 최강, 현존 비공개 상위까지 포함한 실전 최강, 특정 상대에 대한 우위는 다른 주장이다. 현재 c365와 c358은 상위 후보로 유지할 근거가 있지만, c365 확정 우위나 모든 공개 강자 압도는 아직 미확인이다.

수정 우선순위는 결과 유효성 방어·실행 격리 → 호환 계약/중복 표본 구분 → 상위권 대전과 seed 단위 불확실성 표시다. 이번 검토에서는 구현하지 않았다.
