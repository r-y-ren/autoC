## 3. STEP 2: ROUTE_VRP_MISS_ON (default OFF), cells
All code is in `route_vrp._miss_retry`, called in solve_plan after the ROUTEOPT2 retry, and only while the day is still unsolved.

| cell | what | notes |
|---|---|---|
| M1 | re-solve with construct misses repaired (Solver._repair: regret-2 + one ejection chain) | = "the second repair pass" |
| M2 | spawn-robust re-solve (`_robust`) | Every hire's route is searched from start + 2. The access tiles are a 2x2 block, so a route that is feasible from its planner spawn at start + 2 is feasible from any access tile at start. Then the true starts are restored, the sequential engine spawns are computed once and re-checked as a fixed point, and every route is re-evaluated. |
| **M3** | M1, then M2 (with the repair inside) | the cell judged |
| M4 | M3, then ROUTEOPT2 freeze rounds 1-2 (the last hires stay on the planner's rows) | = "the better fallback" |

- `ROUTE_VRP_MISS_EXTRA_S` raises the apply deadline (and the checkpoint-restore window) on the unsolved day only.
- The judge counter is `KAGG3_VRP_MISSLOG`.
- The test is `tests/test_route_vrp_miss.py`: 7 pass on three live miss dawns (5 cell tests + 2 M3-P gate tests). On the d14 rep day and the d11 robust day, M1 solves the first and M2 the second, and M3 and M4 solve both. The d20 day is unsolved by every cell.

**M3-P** (added on the coordinator's 20:37Z request) is `ROUTE_VRP_MISS_PROG_ONLY`: the retry runs only on programme-coded seats. It uses the LATCHHERD1 melon rule (the rival holds 1..10 MELON plantings at d2 h0), computed by `runtime._miss_latch` once per game and handed to the router every turn.

**Why only M3 was judged.** The HARNESS2 and V56 judges run without a deadline (SAFETY_S 1e9), so the deadline knob has no effect there. M1 and M2 are M3's two halves, and the harness miss log shows both halves firing.
