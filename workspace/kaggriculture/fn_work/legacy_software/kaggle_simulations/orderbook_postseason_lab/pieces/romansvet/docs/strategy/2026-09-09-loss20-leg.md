# The LOSS20 leg (2026-09-09)

`S/loss20/` — the LOSS12 judge leg widened from twelve pinned-town tapes to twenty.

## Why

`S/loss12/` was cut on 2026-09-09 because flow166 trains on all 42 non-family pinned gate
tapes, so `S/lossflip`'s HELD-OUT line stopped being held out. Twelve boards is a thin
judge: the first candidate sweep returned a seat-grouped `t` of only +1.25 on a d-margin of
+2,467 (`S/loss12se/out.txt`) — the mean was worth having, the significance was not. Eight
further losses of sub 56098262 have since been cut into pinned-town tapes, so the leg now
runs on all twenty: 20 opponents x 2 seats x 1 seed = 40 games, ~+67 % more boards under the
same wall clock per arm.

## The id list (order is load-bearing)

`S/loss20/ids.txt` = the twelve LOSS12 ids **in their existing order**, then the eight later
cuts:

```
107056463 107067869 107068399 107070717 107072760 107079367 107081922 107088554
107090008 107089992 107092814 107095149            <- the LOSS12 twelve, order frozen
107108124 107109832 107116818 107125425 107131313 107134203 107140814 107144702
```

All twenty were verified 2026-09-09 to have both `artifacts/tape_actions_town/<id>.npz` and
`artifacts/panel_opp_town/opponent_tape_<id>/main.py`, and all twenty appear in
`S/band2100p/town_schedules.json` (the pinned-town schedule the leg exports). None was
dropped.

`--seed-per-opponent` draws `seed_base + SEED_STRIDE*(i+1)` off the **list index**
(`scripts/eval_vs_baselines.py:53-73`), and the index depends on the position only, never on
the list length. Keeping the twelve first therefore hands those tapes the *same* seeds in
LOSS20 as they had in LOSS12 — the eight new ids simply take fresh indices 12..19. Never
reorder or insert: the moment an index moves, the base csv stops pairing and every delta
becomes a board lottery instead of a paired measurement.

## Files

| file | role |
| --- | --- |
| `S/loss20/ids.txt` | the twenty ids, order frozen |
| `S/loss20/run.sh` | `run.sh <name> [<worktree>] [<theta.npy>]` — one arm; writes `S/lossflip/<name>_loss20.csv`, `S/loss20/<name>.log`, `S/loss20/<name>.summary`, ends `LOSS20DONE` |
| `S/loss20/flips.py` | reader; `LOSS20 (...)` line + the seat-grouped SE/t line |
| `S/loss20/chain.sh` | base then the three candidates, sequentially; appends to `S/loss20/chain_summary.txt`, ends `LOSS20CHAINDONE` |

The 12-id LOSS12 leg is untouched and still runs on its own `ids.txt` and its own
`*_loss12.csv` files; loss12 rows pair only with loss12 rows, loss20 rows only with loss20.

## The statistic

`flips.py` prints two lines per arm:

```
LOSS20 (20 ids, 40 games): base win X -> Y  FLIPS +a DROPS -b  d-margin Z
LOSS20 SE: boards 20  mean M  sd S  SE E  t T   (seat-grouped, S/bank/paired.py)
```

The `t` is the seat-grouped one: both seats of a board are averaged into ONE observation on
`(seed, opponent)` before the spread is taken, exactly as `src/kagg3/es/train.py`'s
`paired_stats(group_seats=True)` and `S/bank/paired.py` do it. The two mirrored games are
near-duplicates — frequently byte-identical margins, always the same market draw — so a
row-level `t` over 40 rows is inflated by roughly 1.4x
(`docs/strategy/2026-09-09-lottery-audit.md` s4.1) and must not be used to decide anything.
With 20 boards instead of 12 the SE falls by ~sqrt(12/20) = 0.77x for the same spread.

A smoke test of the reader against the existing loss12 csvs reproduced the published LOSS12
numbers for flow166_g170 exactly (`FLIPS +4 DROPS -0 d-margin +2467`, seat-grouped
`t +1.25`), confirming the widened reader is a faithful generalisation and not a new
statistic.

## The run

`S/loss20/chain.sh` plays, sequentially and each at `--workers 8` (the machine is loaded;
never two legs at once):

1. `flow135_g350` — the live 4,980-param base, from worktree `agent-a85c50163fb5dcbb7`.
   It must run first: it writes the csv every candidate pairs against.
2. `flow166_g170`, `flow167_g150`, `flow166_g150` — the 6,789-param candidates, from
   worktree `arms-next`.

All four thetas live in the main repo's `artifacts/kagg2_games/thetas/`; only the worktree
(i.e. `src/`) differs between the base and the candidate arms, because the two theta widths
decode against different planners.

Launched detached 2026-09-09 ~17:50Z. Budget ~5-8 min per arm at 8 workers, so ~25-35 min for
the chain.

## How to read the result

Grep `S/loss20/chain_summary.txt` for `LOSS20`; the file ends `LOSS20CHAINDONE`. The prize is
a candidate whose seat-grouped `t` clears ~2 on 20 boards while `DROPS` stays low — a
d-margin with FLIPS but no significance is the same board lottery LOSS12 could not resolve.
