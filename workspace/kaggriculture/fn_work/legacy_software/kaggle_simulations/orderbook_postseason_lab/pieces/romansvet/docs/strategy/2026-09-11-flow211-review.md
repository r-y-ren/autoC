## Defects, ranked

### D0 — HIGH (launch risk). The abs probe is the peak-memory event, `--chunk` **cannot** bound it, and it scales with the rung count — which is exactly what flow211 changes.

The launcher header (`S/flow211/launch_flow211.sh:152-161`), README:19,67 and the staging doc:102 all
rest on one claim: *"Device memory in this trainer is set by `--chunk`, not `--pop` or `--episodes`."*
That is true of the main evaluation loop (see passed check 9) and **false of the abs probe**:

`src/kagg3/es/train.py:5510` — `limit = max(int(self.cfg.chunk), total)`

`max`, not `min`. The comment two lines above says so outright: *"At the live `--chunk 8192` nothing
splits at all."* The probe therefore runs as **one unsplit jit call** of
`total = 2 * abs_pairs * r` rows (`:5462`), where `r = len(rungs)` (`:5459`) is the whole ladder —
the 4 archetypes plus **every** tape rung, which are appended to the archetype list at `:3874-3876`.

| | r | probe rows = 2 x 64 x r |
|---|---:|---:|
| flow209 | 4 + 166 = 170 | 21,760 |
| **flow211** | **4 + 196 = 200** | **25,600 (+17.6 %)** |

So the answer to "does `--episodes 200` change the abs probe or GPU memory" is **no on both counts**
(the probe is a function of `--abs-pairs` and the rung count, never `cfg.episodes`), but the
**30 new rungs raise the run's single largest allocation by 17.6 %**, and it is 3.1x the main loop's
8,192-row step. It is also allocated *concurrently* with the generation that calls it —
`absolute_report` is invoked from inside `generation()`'s frame (`:5055`) with `thetas` (111 MB),
`eps` (56 MB), `money`, `mine`, `theirs` and `adv` still bound. The 25,600-row shape is one flow209
has never compiled, so it is also a new XLA compile. `--best-replicate 2` (`:5118-5130`) fires up to
two more full-size probe calls on each accepted record (sequential, so not additive to peak).

This is the only genuine OOM candidate in the change, and the staging doc explicitly rules it out on
a claim that does not hold. Mitigating detail: `--abs-every 10` means the first probe fires at
**gen 10**, roughly two hours in — an OOM would not show at gen 1.

**Fix (one of):** (a) accept and watch gen 10 explicitly — add it to the launch checklist rather than
asserting memory cannot move; (b) drop `--abs-pairs 64 → 54` to hold the probe at flow209's
21,600 rows (changes the abs yardstick, so only if (a) is unacceptable); (c) correct the header,
README:19,67 and staging doc:102 to say `--chunk` bounds the *main loop only* and the probe scales as
`2 x abs_pairs x (4 + n_tapes)`. **(c) is required regardless** — the claim as written will mislead
the next arm, and a NEXT60 extension would take the probe to ~29,000 rows.
`src/kagg3/es/train.py:5459-5462,5510`; `S/flow211/launch_flow211.sh:152-161`;
`S/flow211/README.md:19,67`; `docs/strategy/2026-09-11-flow211-staging.md:102`.

### D3 — MEDIUM-HIGH (read-corrupting). `--seed 309 → 311` breaks the pairing the README claims.

`S/flow211/launch_flow211.sh:333` carries `--seed 311` against flow209's `--seed 309` (confirmed in
`~/stage_hr/artifacts/flow209/config.json`: `seed = 309`). README:15 and the staging doc:41 call this
"fresh arm, fresh draw sequence", but README:110-113's Reading rule says the flow209/flow211 pair
"isolates the **objective**". It does not: the ES perturbation stream differs, so the comparison
confounds the objective with a seed draw — the same ±5-10 pt lottery the noise-floor work has been
fighting all week.

Reusing 309 is safe here, because the boards are not seed-derived: `--pinned-fixed-seed` puts every
pinned rung on `pinned_seed_word(name)`, a blake2b of the ladder label only
(`src/kagg3/es/train.py:1316-1331`). Only the perturbations and the 4 self-play draws would be
shared, which is precisely the CRN pairing an objective-only A/B wants.

**Fix:** `--seed 311` → `--seed 309`, or delete the "isolates the objective" claim and state that
flow209-vs-flow211 is unpaired.
`S/flow211/launch_flow211.sh:333`, `S/flow211/README.md:15,110-113`.

### D4 — MEDIUM. `mean_win` is an **unweighted** episode mean; it is not 38 %-weighted and is not comparable to flow209's curve.

`src/kagg3/es/train.py:5009` — `win = win_scores(mine, theirs).mean(axis=1)`. The rung weighting
(`ep_weight`, built at `:4979` by `pinned_weights` `:4478-4491` and passed at `:4994`) reaches
`shaped_advantage` — i.e. the **gradient** — and nothing else. The deliberate comment at `:5007-5008`
says why: "Logged in win-rate units regardless of what the gradient consumed, so `mean_win` stays
comparable against every earlier run's curve."

So the answer to "does `mean_win` become a NEXT30-dominated 38 % number" is **no**: NEXT30 is 30 of
200 episodes = **15 %** of `mean_win`, while carrying **38.16 %** of the objective weight. The
README and staging tables are arithmetically correct and consistently labelled "weight"/"share" — no
wrong claim was found — but neither warns that the logged curve is unweighted. The trap is the
comment's own premise: `mean_win` is comparable across runs only when the *episode composition* is
the same, and flow211 changes it twice (30 new, harder 2550-2750 boards in; self-play tail 12 → 4
episodes). flow209's observed 0.667 baseline will drop mechanically, not because the theta is worse.

**Fix:** one line in the Reading rule: "`mean_win` is unweighted (`es/train.py:5009`) and its episode
composition changed — read `best`, the gate RECORD lines and the held-out legs; never flow211's
`mean_win` level against flow209's."

### D5 — MEDIUM. `precheck.sh:176` greps for a warning string this configuration cannot emit — the check can never fail.

`S/flow211/precheck.sh:176` runs `grep -q 'WARNING: --pinned-once with --episodes'`. That string is
the `carried < 0` branch at `scripts/train.py:189-195`. flow211 has `carried = 200 − 196 = 4`, so
that branch is unreachable; the branch that **will** fire is `scripts/train.py:196-201`
(`elif carried < 2 * n_pinned:` → `WARNING: --pinned-once leaves {carried} episodes for …`), since
`4 < 392`. flow209's own log proves the shape:

```
pinned-once: 166 pinned rungs x 1 episode + 13 episodes carried
WARNING: --pinned-once leaves 13 episodes for 4 unpinned rung(s) and self-play, against 166 pinned
boards -- at this ratio the drawn rungs and the pool are sampled thinly.
```

The precheck therefore prints `PASS  no --pinned-once episode-budget warning from the trainer` on a
run that does warn. It is a check that cannot fail, which is worse than no check.

**Fix:** `grep -q 'WARNING: --pinned-once'`, and make the expected "sampled thinly" warning a NOTE
rather than a FAIL (it is benign and intended here — the residual is deliberately 4).
`S/flow211/precheck.sh:176-180`; also `S/flow211/README.md:62` ("no warning" for option (a)) is
wrong for the same reason — option (a) warns too, just about thin sampling instead of overspend.

### D6 — MEDIUM. The busy-GPU guard dies silently instead of refusing when `nvidia-smi` fails.

`S/flow211/launch_flow211.sh:272` — `busy=$(nvidia-smi --id="$GPU" --query-compute-apps=pid --format=csv,noheader | wc -l)`
under `set -euo pipefail` (`:264`). Verified by direct test: with `pipefail`, a failing first stage
makes the assignment inherit the non-zero status and `set -e` exits **at line 272**, before the `if`
at `:273` — no `REFUSED` line, exit code 1 or 6, and an empty `artifacts/flow211/launch.out`. On the
host, `nvidia-smi --id=2` returns rc 6 ("No devices were found"). The same path is taken if
`CUDA_VISIBLE_DEVICES` holds a UUID list or `0,1`, which `:271` feeds straight into `--id`.

The guard is otherwise **correct**: verified live that `--id=0` → `981991` and `--id=1` → `982269`
(one line each, both the running arms) and that an idle card returns nothing → `busy=0`. It cannot
pass on a busy GPU nor refuse on an idle one.

**Fix:**
`busy=$(nvidia-smi --id="$GPU" --query-compute-apps=pid --format=csv,noheader | wc -l) || { echo "REFUSED: nvidia-smi --id=$GPU failed" >&2; exit 3; }`.

### D7 — LOW. Three independent hard-coded copies of "166" / "198" / "200".

`S/flow211/launch_flow211.sh:306` `N_PINNED=$(( 166 + ${#NEXT_IDS[@]} ))` hard-codes 166 rather than
counting `INHERITED_IDS` (`:268`); the `-gt 198` refusal at `:308` is a second constant held against
the `--episodes 200` literal at `:328`. And `INHERITED_IDS` is itself a *third* copy of the list — it
is used **only** by the duplicate guard at `:302`, never to build `--tape-actions` (`:321`), so if it
ever drifted from the literal list the guard would silently disarm.

Verified today that all three agree exactly: `INHERITED_IDS` (166) == the 166 literal
`--tape-actions` ids == the 166 literal `--rung-weight` ids, no duplicates, and NEXT30 disjoint from
all of them. So this is latent, not live.

**Fix:** `N_PINNED=$(( $(tr ',' '\n' <<<"$INHERITED_IDS" | grep -c .) + ${#NEXT_IDS[@]} ))` and derive
the cap from the `--episodes` literal instead of restating it.
