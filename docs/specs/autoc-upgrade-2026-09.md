# autoC 工作流升级 spec（2026-09）

## Problem Statement

用户视角的问题：

1. 自备的 my_LLM_valut 深度精读库（900M，UAV/空中边缘计算/LLM 前沿，Karpathy LLM-Wiki 模式）躺在项目根目录：知识无法被慢循环知识库（kb/）检索与引用，高价值情报进不了选赛决策，且违反根目录纪律。
2. 外来资料（赛事章程 PDF、论文、他人分享的材料）没有正式投递入口，只能散落对话或手工塞进战役 references，下次知识库更新时不会被自动发现与整合。
3. 交付链路没有利用已装的三套技能资产：/attack 决策缺少对用户的逼问式澄清；/deliver 的实现规格派生只有蓝图粗粒度任务包，缺少 spec/ticket 级细化与实现者自检；验收通过后生成答辩 PPT 需人工另起会话。
4. 两台电脑接力维护，但知识库更新、契约版本、插件装机的不同步会造成静默错配（旧 schema 拒新蓝图、缺插件使自动链失效、双机 cron 互撞）。

## Solution

用户视角的解法：

- **慢循环**：一次性有监督跑批把 valut 提炼成带论文标题溯源的 kb 技术卡；新增 kb/inbox/ 投递口——丢文件零门槛，sync 跑批自动分类消化，未溯源资料只作线索不进分析。
- **快循环**：/attack 在蓝图前加完整 grilling；蓝图确认后（开关默认开）自动跑 to-spec → to-tickets → implement 一口气到完成再汇报；任务包内实现者自检通过才报波门；/accept 通过后用 /ppt 从项目文档总结内容简报并走 ppt-master 双门生成正式答辩 PPT；/ppt-self 提供同阶段人工副驾。
- **多机**：接力纪律入册；契约版本播报 + 插件可用性检查把错配变成开机即见。

## User Stories

1. 作为维护者，我想把任意资料文件丢进 kb/inbox/，这样它会在下次知识库跑批时被自动分类整合，而不需要我手动建条目。
2. 作为维护者，我丢文件时可以顺手放一个同名 .meta.yaml 写明来源，这样资料能直接晋级为可引用条目。
3. 作为维护者，即使我忘了写 meta，文件也不会被拒收或删除，而是作为未溯源线索保留并在跑批报告里被点名提醒补源。
4. 作为维护者，我想让跑批消化 inbox 受配额保护，这样一次丢一大堆文件也不会把单次跑批预算烧穿，剩余文件留到下轮。
5. 作为 KB 采集角色，我想在每次 sync 跑批里先检查 inbox，这样维护者丢的资料不会无限期积压。
6. 作为维护者，当丢入资料涉及活跃战役（如赛制更新）时，我想在跑批报告里看到提示、由我决定是否在战役会话中引用，而不是被自动改动战役。
7. 作为维护者，我想让 my_LLM_valut 的 wiki 页按比赛相关性提炼成 kb 技术卡，这样选赛决策能检索到 UAV/MEC/LLM 前沿情报。
8. 作为维护者，我想让每张提炼卡在正文标注来源论文标题、并尽力从 bib 回填 DOI/URL，这样我能溯源到原始论文。
9. 作为维护者，我想让收录/拒绝决策落在拒绝台账里，这样"提炼了什么、跳过了什么"可审计，方向卡不足时还可回补。
10. 作为维护者，我想让提炼跑批在独立分支上波次推进、断点可续，这样中途失败不必从头再来，另一台机器也不会拉到半成品 kb。
11. 作为维护者，提炼完成并校验收录后，我想整目录删除 my_LLM_valut，这样项目根恢复干净（Obsidian 有备份）。
12. 作为维护者，我在 /attack 时想先被完整 grilling（多轮问到无遗漏分支），这样蓝图建立在被逼问清楚的需求上。
13. 作为维护者，我在确认蓝图时能看到 auto_chain 开关，这样"这次交付要不要自动跑规格链"在唯一人工闸门处一并拍板。
14. 作为主会话（协调者），蓝图确认后我想派发 planner 跑 to-spec/to-tickets，这样规格派生不占主会话上下文（瘦协调纪律）。
15. 作为 software 实现者，我想在任务包内拿到 ticket 级细化规格，这样我知道精确的实现边界与验收对应项。
16. 作为 software 实现者，我想按 verification-before-completion / TDD 纪律自检通过后才报波门，这样波门检查不再是我第一次发现自己的错误。
17. 作为维护者，自动链一口气跑到 implement 完成才汇报，这样我不需要中间盯梢（避免退化成伪 /self）。
18. 作为维护者，/accept 仍是我唯一的验收人工门，自动链与自检都不得新增人工检查点。
19. 作为维护者，验收通过后我想用 /ppt 从最终报告+蓝图+验收记录+metrics 总结一份内容简报，这样 PPT 内容可溯源、可归档、换工具不用重写。
20. 作为维护者，/ppt 走 ppt-master 自带的 Gate1/Gate2，这样沟通契约与模板选择仍由我拍板。
21. 作为维护者，正式答辩 pptx 只有 /ppt 一条产线、Marp 只作波内草稿，这样归档时不会出现两份正式 PPT 打架。
22. 作为维护者，我想用 /ppt-self 进入 PPT 阶段的人工副驾模式，这样我可以亲自掌控细节而 agent 打下手。
23. 作为另一台机器上的维护者，我开工前 pull、收工 push，这样接力交接以远程为唯一事实源。
24. 作为维护者，一台机器跑 KB 维护、另一台做战役时互不干扰，这样分工并行是安全的（子树不相交 + 状态本机隔离）。
25. 作为另一台机器上的维护者，我开机就能看到契约版本与插件缺失警示，这样旧版本/缺插件不会被静默带病运行。
26. 作为维护者，归档 tag 会被 push（--tags），这样另一台机器能看到归档标记。
27. 作为维护者，KB 深度跑批 cron 只在一台机器启用，这样无人值守时不会双机互撞。

## Implementation Decisions

按域名词汇表述（不落具体文件路径）：

1. **蓝图契约地位不变**：blueprint 仍是唯一契约与验收锚点；mattpocock 链是蓝图之下的工作层，产物落战役根 specs 区；验收项 ID 前缀仍出自蓝图。
2. **K-02 增加 grill 前置步**：完整 grilling（多轮、无轮次上限），以 KB 索引与相关条目为文档语境，产出 grill 笔记作为 strategy/blueprint 输入；蓝图呈报确认为第二次交互（唯一人工闸门不变）。
3. **蓝图 schema 增量**：`workflow.auto_chain` 布尔字段，默认 true。
4. **自动链语义**：蓝图确认后 to-spec → to-tickets → implement 直通到完成再单次汇报；中间产物（spec/tickets）存档战役根可随时翻阅，不设中途人工门。
5. **新增 planner 角色**：deliver 首波前派发，跑 to-spec/to-tickets；ticket 按 milestone × owner_role 归组为任务包；波次拓扑仍由蓝图 milestones 依赖关系决定（ticket 不改变拓扑）。
6. **包级自检**：software 角色章程加入自检条款（verification-before-completion / TDD 纪律），自检通过是报波门的前置；波门五查继续兜底跨包契约；不加互审。
7. **新增 K-12 /ppt**：窗口为验收通过后、归档前；document 角色先产内容简报（数字只出自 metrics），随后走 ppt-master Default 路线、其自带 Gate1/Gate2 为用户门；ppt-master 项目目录路由进战役 docs 子树；Marp（K-06）降为波内草稿。
8. **新增 K-13 /ppt-self**：PPT 阶段副驾模式，豁免范围限 docs 子树，语义沿用 /self。
9. **守卫策略修正**：verify 态现仅放行 acceptance/，需为"验收通过后"增加 docs 子树放行窗口（或等价子态），其余守卫行为不变。
10. **tech-card schema 增量**：`venue_tier / evidence_tier / paper_role / reproducibility_level` 四个可选受控枚举；存量卡零迁移，老化重验时顺补；提炼卡强制填写。
11. **sources 增 paper-distill 形态**：{论文标题, doi/url（bib 可回填时）, distilled_from, distilled_date}。这是对铁律 1"URL+抓取日期"的**受控放宽，边界仅限本次提炼跑批**，须写入全局纪律文档。
12. **inbox**：kb 根下独立投递目录 + README 约定；gitignore（本机暂存区，消化产物才入库）；sidecar meta 可选（source_url / dropped_at / 备注 / 意向方向）；无 sidecar 照收为未溯源线索，只进 raw 不进分析条目；消费发生在 K-01/K-08 跑批内（collect 态已有写权，零守卫改动）；路由三分：赛事章程→条目增补/新候选、论文技术→技术卡候选队列、不可归类→线索区+报告点名；每轮受预算配额，剩余保留不删。
13. **vault-distill**：复用全量构建模式（停双机 cron、配额豁免、主题分片派发子 agent、波次 commit 断点可续）；独立分支进行、完成合并回主干；收录/拒绝落拒绝台账；raw 未编译论文原则上不提炼（wiki 是其编译产物），方向卡不足时例外回补；完成后删除源目录（用户已批准此不可逆操作）。
14. **多机协作节入册**：接力纪律（开工 pull --rebase、阶段 commit 即 push、远程为交接唯一事实源、归档后 push --tags）；deep-sync cron 单机启用、换主力机时迁移；"一台 KB 维护 + 一台战役"分工并行明文认可（子树不相交 + 本地态隔离）。
15. **契约版本机制**：schema/skills/agents 变更时 bump 契约版本（沿用 state schema_version 惯例）；SessionStart 播报版本，脚本侧校验防错配。
16. **插件依赖**：文档列插件清单+版本+安装命令（mattpocock / ppt-master / superpowers / document-skills）；SessionStart 增加插件可用性检查，缺哪个警示哪个。
17. **升级过程特例**：本升级窗口内，工作流自身要求被用户显式暂停（钩子已关）；技能所需文件允许产生，升级完毕后统一清理。
18. **落地顺序**：A 线基础设施（schema / inbox / 技能修订）→ vault-distill 跑批 → 校验收录 → 删源目录 → B 线落地；全程单机执行、每步 commit 即 push。

## Testing Decisions

好测试的标准：只测外部行为（放行/拒绝/产出物形态/报告内容），不测内部实现细节。缝越少越好，主力缝唯一：

- **主力缝＝端到端彩排战役**（唯一新增缝，最高层）：落地后用一次性小战役走完整新链路（grill → 蓝图含开关 → planner/自动链/自检 → accept → ppt），通过即行为验收。先例：框架战役自身。
- **schema/lint 现有缝**：新枚举字段正例/负例（非法枚举值必须被拒）、蓝图新字段默认值与校验。先例：lint 的隔离区路径。
- **守卫现有缝**：以构造状态直接调守卫脚本，验证 docs 放行窗口与既有不变量不变（archive 只读、未登记战役根拒写等）。先例：fail-closed 行为。
- **跑批脚本现有缝 + 小样本**：inbox 用三类 fixture（全 meta / 缺 meta / 超配额）断言路由与报告；vault-distill 先在十余页样本 + 假 bib 试跑（断言标题标注与 DOI 回填），通过后全量。先例：全量构建的波次断点纪律。
- **SessionStart 缝**：直接调 hook 断言版本行与插件检查行。
- **不测**第三方插件内部（ppt-master / mattpocock / superpowers 视为外部依赖，只验证可用性检查能发现其缺失）。

## Out of Scope

- 跨包互审（code-review 互查）：留到实际出现接口错配再加。
- 存量 90 卡新字段的强制迁移：仅老化重验时顺补。
- 并行式多机的 state 投影同步文件：本轮只落接力纪律，投影方案留档备选。
- RSSHub 等自动信源接入（方向模板待定项维持待定）。
- Marp 产线的移除或重做（仅降级为草稿）。
- 对 ppt-master / mattpocock / superpowers 插件内部的任何修改。
- inbox 对活跃战役 references/ 的自动写入（慢快循环保持解耦）。
- 硬件/物理测试与 ACM 边界备忘的任何变更。
